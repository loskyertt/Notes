# 1.构建指令

现代 CMake 提供了更方便的 `-B` 和 `--build` 指令，不同平台，统一命令！

在源码目录用 `-B` 直接创建 `build` 目录并生成 `build/Makefile`：

```bash
cmake -B build
```

这种方式免去了先创建 build 目录再切换进去再指定源码目录的麻烦。

示例如下：
![示例1](https://s2.loli.net/2024/11/29/tL9qsWvMekI3zcw.png)

自动调用本地的构建系统在 build 里构建，相当于 `make -C build -j4`：

```bash
cmake --build build -j4
```

这种方式统一了不同平台（Linux 上会调用 `make`，Windows 上调用 `devenv.exe`）

调用本地的构建系统执行 `install` 这个目标，即安装：

```bash
sudo cmake --build build --target install
```

相当于 Linux 下的 `sudo make install`。

> 结论：从现在开始，如果在命令行操作 CMake，请使用更方便的 `-B` 和 `--build` 命令。

# 2.生成器

- Linux 系统上的 CMake 默认用是 Unix Makefiles 生成器；Windows 系统默认是 Visual Studio 2019 生成器；MacOS 系统默认是 Xcode 生成器。
- 可以用 `-G` 参数改用别的生成器，例如 `cmake -G Ninja` 会生成 Ninja 这个构建系统的构建规则。Ninja 是一个高性能，跨平台的构建系统，Linux、Windows、MacOS上都可以用。
- Ninja 可以从包管理器里安装，没有包管理器的 Windows 可以用 Python 的包管理器安装：pip install ninja（有趣的是：CMake 也可以通过 `pip install cmake` 安装）。
- 事实上，MSBuild 是单核心的构建系统，Makefile 虽然多核心，但因历史兼容原因效率一般。而 Ninja 则是专为性能优化的构建系统，它和 CMake 结合都是行业标准了。

```bash
cmake -B build -G Ninja
```

注：`-G Ninja` 还可以写成 `-GNinja` 和 `-G "Ninja"`。在 Linux 上没有指定的话，默认是 `-G "Unix Makefiles"`。

如图所示：
![示例2](https://s2.loli.net/2024/11/29/5veQ3nHVUhT7ipl.png)

## 2.1 Ninja 和 Make 的简单对比：

`ninja` 花费的时间：
![ninja.png](https://s2.loli.net/2024/11/29/sha1dGMkHTNuQ8A.png)

`make` 花费的时间：
![make.png](https://s2.loli.net/2024/11/29/kfcOwtZbQV4UMA5.png)

从两幅图对比可以看出，`ninja` 花费的时间更少，效率更高。

事实上，在性能上：`Ninja > Makefile > MSBuild`。Makefile 启动时会把每个文件都检测一遍，浪费很多时间。特别是有很多文件，但是实际需要构建的只有一小部分，从而是 I/O Bound 的时候，Ninja 的速度提升就很明显。然而 NVIDIA 的 CUDA toolkit 在 Windows 上只允许用 MSBuild 构建，不能用 Ninja。

## 2.2 MSBuild 生成器

如果是要用微软的 MSBuild 生成器：

```bash
cmake -B build -G "Visual Studio 17 2022" -DCMAKE_BUILD_TYPE=Debug
```

> 比如使用 VS 2022 进行构建。

# 3.设置

## 3.1 编译器设置

可以在 CMakeLists.txt 中添加：

```CMake
set(CMAKE_C_COMPILER clang)
set(CMAKE_CXX_COMPILER clang++)
```

指定编译器为 clang 和 clang++。不指定的话，默认是 gcc 和 g++。

> 这两条命令应该放在文件的开始位置（`cmake_minimum_required` 之下，其他命令之上），否则可能无效。

也可以在命令行阶段指定（**推荐**）：

```bash
cmake -B build -G Ninja -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++
```

## 3.2 CMake 路径变量

### 3.2.1 常见源码路径变量

| 变量 | 含义 | 常见用途 |
|---|---|---|
| `CMAKE_SOURCE_DIR` | 顶层源码目录 | 顶层工程专用 |
| `PROJECT_SOURCE_DIR` | 当前 `project()` 对应的源码目录 | 当前项目或子项目根目录 |
| `CMAKE_CURRENT_SOURCE_DIR` | 当前正在处理的源码目录 | 当前 `CMakeLists.txt` 所在目录 |
| `CMAKE_CURRENT_LIST_DIR` | 当前正在执行的 CMake 文件所在目录 | `.cmake` 模块内引用旁边文件 |

> [!tip]
> 在 `xxxConfig.cmake` 中，通常使用 `CMAKE_CURRENT_LIST_DIR`，因为它指向当前这个配置文件所在目录。

### 3.2.2 示例

假设在一个叫 `PROJECT` 的目录中，`*.cmake` 或者 `CMakeLists.txt` 中不同变量表示的目录范围如下：

| 变量 | 含义 | 在项目中的值 |
| :--- | :--- | :--- |
| `CMAKE_SOURCE_DIR` | **顶层 `CMakeLists.txt` 所在目录（项目根目录）**| `C:/.../PROJECT` |
| `PROJECT_SOURCE_DIR` | 当前 `project()` 所在目录（通常同上）| `C:/.../PROJECT` |
| `CMAKE_CURRENT_SOURCE_DIR` | **当前** `CMakeLists.txt` 所在目录 | `C:/.../PROJECT/example` |

比如项目结构是这样的（我的项目目录名是 `EasyX_learn`，其它目录省略）：

```shell
.
│ 
│   CMakeLists.txt
│
├───example
		CMakeLists.txt
		example01.cpp
```

在 `./CMakeLists.txt` 和 `./example/CMakeLists.txt` 中分别写上：

```cmake
message(STATUS "CMAKE_SOURCE_DIR : ${CMAKE_SOURCE_DIR}")
message(STATUS "PROJECT_SOURCE_DIR : ${PROJECT_SOURCE_DIR}")
message(STATUS "CMAKE_CURRENT_SOURCE_DIR : ${CMAKE_CURRENT_SOURCE_DIR}")
```

输出分别是如下这样：

- `./CMakeLists.txt` 中：

```shell
-- CMAKE_SOURCE_DIR : C:/Users/sky/Desktop/Dev/EasyX_learn
-- PROJECT_SOURCE_DIR : C:/Users/sky/Desktop/Dev/EasyX_learn
-- CMAKE_CURRENT_SOURCE_DIR : C:/Users/sky/Desktop/Dev/EasyX_learn
```

- `./example/CMakeLists.txt` 中：

```shell
-- CMAKE_SOURCE_DIR : C:/Users/sky/Desktop/Dev/EasyX_learn
-- PROJECT_SOURCE_DIR : C:/Users/sky/Desktop/Dev/EasyX_learn
-- CMAKE_CURRENT_SOURCE_DIR : C:/Users/sky/Desktop/Dev/EasyX_learn/example
```

> `CMAKE_SOURCE_DIR` 比 `PROJECT_SOURCE_DIR` 更推荐。

# 4.查找第三方库（非默认路径）

> 有时安装的第三方库没有安装在 CMake 可自动搜索到的路径中，此时需要由用户手动设置。

## 4.1 方式一：list(APPEND ...)

> 适用于 **标准安装结构** 的第三方库。

**作用**：该命令的目的是将一个新的路径 **添加** 到 CMake 的 CMAKE_PREFIX_PATH 变量中，让 CMake 在该路径下查找依赖库（`find_package` 查找时会用到）。

示例：

```cmake
list(APPEND CMAKE_PREFIX_PATH "C:/packages/opencv-4.12.0-mingw")
find_package(OpenCV REQUIRED)
```

CMake 会在这个前缀下按标准结构搜索：

```plain
<prefix>/lib/cmake/opencv4/OpenCVConfig.cmake
<prefix>/lib/cmake/OpenCV/OpenCVConfig.cmake
<prefix>/share/OpenCV/OpenCVConfig.cmake
...（还有其他标准路径）
```

可以同时添加多个路径：

```cmake
list(APPEND CMAKE_PREFIX_PATH
  "C:/packages/glfw-3.4"
  "C:/packages/glew-2.3.1"
)
```

## 4.2 方式二：set(Package_dir "...")

> 如果方式一不行，可以采用 `set(Package_dir "...")` 方式。

示例：

```cmake
set(OpenCV_DIR "C:/packages/opencv-4.12.0-mingw/x64/mingw/lib")
find_package(OpenCV REQUIRED HINTS ${OpenCV_DIR})
```

> `OpenCV_DIR` 是自定义变量，`HINTS` 是 **额外的提示路径**。CMake 直接到 `C:/packages/opencv-4.12.0-mingw/x64/mingw/lib` 这个目录找 `OpenCVConfig.cmake`，**不搜索其他位置**。CMake 本身对 `OpenCV_DIR` 变量没有特殊处理，它可以在代码中手动使用，比如直接传递给 `find_package()` 的 `HINTS` 参数。

**适用场景**：
- 你知道确切的 `.cmake` 文件位置
- OpenCV 安装结构非标准
- 需要强制使用特定版本的 OpenCV

## 4.3 方式三：set(CMAKE_PREFIX_PATH "...")

`set(CMAKE_PREFIX_PATH "...")` 和 `list(APPEND ...)` 这两种方式都是设置 CMAKE_PREFIX_PATH，其区别如下：

| 方式 | 行为 | 风险 |
|------|------|------|
| `set(CMAKE_PREFIX_PATH "...")` | **覆盖**原有值 | 丢失其他库的路径 |
| `list(APPEND CMAKE_PREFIX_PATH "...")` | **追加**到列表 | 保留其他路径，安全 |

示例：

```cmake
set(CMAKE_PREFIX_PATH "C:/packages/opencv-4.12.0-mingw")
```

**假设之前 CMAKE_PREFIX_PATH 已有值**：

```bash
# 之前
CMAKE_PREFIX_PATH = C:/Qt/5.15.2/msvc2019_64;C:/boost

# 执行 set 后
CMAKE_PREFIX_PATH = C:/packages/opencv  ← 原来的路径全没了！
```

这会导致 Qt 和 Boost 找不到了！

> 什么时候可以用 `set(CMAKE_PREFIX_PATH "...")`？

1. 确定 CMAKE_PREFIX_PATH 为空时：

```cmake
# 在项目最开始，确保为空
set(CMAKE_PREFIX_PATH "")  # 清空
set(CMAKE_PREFIX_PATH "C:/packages/opencv-4.12.0-mingw")
```

2. 一次性设置多个路径：

```cmake
# 同时设置多个，覆盖原有值
set(CMAKE_PREFIX_PATH 
  "C:/packages/opencv-4.12.0-mingw"
  "C:/packages/glfw-3.4"
  "C:/packages/glew-2.3.1"
```

> **推荐始终使用 `list(APPEND)`**，除非你有特殊理由需要覆盖！

# 5.链接库

## 5.1 链接时的关键字

`target_link_libraries` 中的 PUBLIC / PRIVATE / INTERFACE，其概念与编译选项一致，但作用对象变成了**库的依赖关系**，影响的是**依赖能否传递给下游**。

- **`PUBLIC`**：传递给链接到此目标的所有目标
- **`PRIVATE`**：仅用于编译此目标，不传递
- **`INTERFACE`**：仅传递给使用者，不用于编译此目标

| 关键字 | 用于自己编译 | 传递给使用者 | 典型用途 |
|--------|-------------|-------------|----------|
| **PUBLIC** | ✅ | ✅ | 有头文件+实现的库 |
| **PRIVATE** | ✅ | ❌ | 内部实现，不暴露头文件 |
| **INTERFACE** | ❌ | ✅ | 纯头文件库、接口库 |

### 5.1.1 PUBLIC

> [!note] `PUBLIC` 适用于“既给自己用，也传递给使用者”。

假设有一个项目的 `3rdparty` 目录中，存放着第三方库的源代码文件（有 `glad` 和 `glfw-3.4` 这两个库）。

1. **glad 设置**：

```cmake
# 3rdparty/glad/CMakeLists.txt
target_include_directories(glad
  PUBLIC ${CMAKE_CURRENT_SOURCE_DIR}/include  # PUBLIC = 传递给使用者
)
```

2. **glfw 设置：**

```cmake
# 3rdparty/glfw-3.4/src/CMakeLists.txt  
target_include_directories(glfw PUBLIC
  "$<BUILD_INTERFACE:${GLFW_SOURCE_DIR}/include>"  # PUBLIC = 传递给使用者
)
```

3. **在项目代码中使用：**

```cmake
# course/CMakeLists.txt
target_link_libraries(${TARGET_NAME}
  PRIVATE opengl32 glfw glad  # 链接时自动获得 PUBLIC 包含目录
)
```

4. **图示说明**：

```
GLAD库设置: target_include_directories(glad PUBLIC include/)
     ↓ (PUBLIC传递)
项目代码: target_link_libraries(lesson01 PRIVATE glad)
     ↓ (自动获得 include 目录)
编译项目代码中的 lesson01 时: 可以找到 #include "glad/glad.h"
```

### 5.2.2 PRIVATE

> [!note] PRIVATE 使用于封装内部实现，只暴露必要的公共接口。因此 `PRIVATE` 主要用于**内部实现细节**，这些头文件或库只需要编译目标本身使用，使用者完全不需要知道。

#### 使用场景

> [!example]
> 源代码示例目录：**源码示例/01_基础教程/example_private**

假设有一个 JSON 库，有公共 API 和内部实现：

```bash
.
├── CMakeLists.txt
├── example_usage.cpp
├── include
│   └── json_parser.h
└── src
    ├── internal
    │   └── string_utils.h
    └── json_parser.cpp
```

`CMakeLists.txt` 中的配置：

```cmake
# JSON库 - 有公共API和内部实现
add_library(json_parser STATIC
    src/json_parser.cpp
    src/internal_utils.cpp
)

# 公共头文件 - 使用者需要
target_include_directories(json_parser
    PUBLIC
        ${CMAKE_CURRENT_SOURCE_DIR}/include
)

# 内部头文件 - 只有自己编译时需要
target_include_directories(json_parser
    PRIVATE
        ${CMAKE_CURRENT_SOURCE_DIR}/src/internal
)

# 内部依赖库 - 使用者不需要知道
target_link_libraries(json_parser
    PRIVATE
        some_internal_lib
)
```

**图示说明 PRIVATE 的作用**：

```
PRIVATE场景：
┌─────────────────────────────────────────────────────────┐
│                json_parser库                            │
│                                                         │
│  PUBLIC include/                                        │
│  ┌─────────────────┐                                    │
│  │ json_parser.h   │ ──► 传递给使用者                   │
│  └─────────────────┘                                    │
│                                                         │
│  PRIVATE src/internal/                                  │
│  ┌─────────────────┐                                    │
│  │ string_utils.h  │ ──► 仅自己编译时使用               │
│  └─────────────────┘                                    │
└─────────────────────────────────────────────────────────┘
           ↓ 使用者只能看到PUBLIC部分
┌─────────────────────────────────────────────────────────┐
│                your_app                                 │
│                                                         │
│  ✅ #include "json_parser.h"     ← 可以找到             │
│  ❌ #include "string_utils.h"    ← 找不到！             │
└─────────────────────────────────────────────────────────┘
```

#### PRIVATE 的好处

1. **隐藏实现细节**

```cmake
# 使用者看不到内部头文件
target_include_directories(json_parser PRIVATE src/internal)
```

- 使用者无法依赖内部API
- 可以随时修改内部实现而不影响使用者

2. **避免头文件污染**

```cmake
# 内部依赖库不会传递给使用者
target_link_libraries(json_parser PRIVATE some_internal_lib)
```

- 使用者不需要知道内部用了什么库
- 避免链接冲突

3. **减少编译时间**

- 使用者不需要处理内部头文件
- 减少包含的依赖数量

### 5.2.3 INTERFACE

> [!note] INTERFACE 只适用于“只给别人用，自己不需要编译”的场景。因此 `INTERFACE` 主要用于**纯头文件库**或者**只提供接口不提供实现的库**。

#### 场景1：纯头文件库

> [!example]
> 源代码示例目录：**源码示例/01_基础教程/example_mathlib**

假设有一个只有头文件的数学库，项目结果如下：

```bash
.
├── CMakeLists.txt
└── include
    └── math.h
```

`CMakeLists.txt` 中的配置：

```cmake
# 纯头文件库 - 没有 .cpp 文件
add_library(math_lib INTERFACE)

# 只需要告诉使用者头文件在哪里
target_include_directories(math_lib
  INTERFACE 
    ${CMAKE_CURRENT_SOURCE_DIR}/include
)

# 不需要编译任何源文件，因为没有实现文件
```

#### 场景2：接口库（定义接口，实现由使用者提供）

> [!example]
> 源代码示例目录：**源码示例/01_基础教程/example_interface**

库结构：

```bash
.
├── CMakeLists.txt
└── include
    └── renderer.h
```

`CMakeLists.txt` 中的配置：

```cmake
# 接口库 - 定义接口，但实现由使用者提供
add_library(renderer INTERFACE)

# 告诉使用者需要链接的系统库
target_link_libraries(renderer
  INTERFACE 
    opengl32
)

# 告诉使用者需要的头文件路径
target_include_directories(renderer
  INTERFACE
    ${CMAKE_CURRENT_SOURCE_DIR}/include
)

# 告诉使用者需要的编译定义
target_compile_definitions(renderer
  INTERFACE
    USE_OPENGL
)
```

**图示说明 INTERFACE 的传递性**：

```
纯头文件库场景：
┌─────────────────┐    INTERFACE    ┌─────────────────┐
│   math_lib      │ ──────────────► │   your_app      │
│ (只有头文件)    │                 │                 │
│ target_include  │                 │ 可以找到        │
│ _directories    │                 │ math.h          │
│ INTERFACE       │                 │                 │
└─────────────────┘                 └─────────────────┘

接口库场景：
┌─────────────────┐    INTERFACE    ┌─────────────────┐
│   renderer      │ ──────────────► │   your_app      │
│ (只有接口)      │                 │                 │
│ target_link_    │                 │ 自动链接        │
│ libraries       │                 │ opengl32        │
│ INTERFACE       │                 │                 │
└─────────────────┘                 └─────────────────┘
```
