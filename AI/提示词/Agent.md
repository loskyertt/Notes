# 1.Git Commit 信息生成

## 1.1 英文描述

```md
# Git 操作专属规则（# 为注释，不生效）
1.  首先全面分析当前项目的所有代码变更（包括新增、修改、删除的文件及代码内容），明确变更的核心用途与类型
2.  编写 Git Commit Message 时，必须遵循 <type>: <description> 规范，严格使用以下合法 tag，禁止自定义未列出的 tag：
    - feat: 新增功能（全新功能开发、业务逻辑新增）
    - fix: 修复问题（bug 修复、异常场景修复、兼容性修复）
    - test: 测试相关（新增测试用例、修改测试代码、完善测试覆盖）
    - docs: 文档变更（修改注释、更新 README、补充接口文档等非代码变更）
    - style: 代码格式调整（仅缩进、空格、命名规范优化，无业务逻辑变更）
    - refactor: 代码重构（无功能新增/删除，仅优化代码结构、解耦、性能优化）
    - chore: 杂项事务（依赖安装/更新、配置文件修改、构建脚本调整等）
3.  Commit Message 描述部分（<description>）要求：
    - 首字母小写，结尾不加标点符号
    - 简洁明了，控制在 50 个字符以内，准确概括代码变更核心内容
    - 避免模糊描述，需具体指向变更模块或功能
4.  执行 Git 操作前，先读取项目根目录的 .gitignore 文件，严格过滤被忽略的文件/目录
5.  仅对非忽略的、有有效代码变更的文件执行 git add 操作（避免添加空文件、临时文件、缓存文件）
6.  完成 git add 后，使用上述规范的 Commit Message 执行 git commit 操作，确保提交成功
7.  git commit 操作完成后，主动询问用户：“是否需要立即执行 git push 操作，将本地提交推送到远程仓库？”
8.  若用户回复“是”“需要”等肯定性表述，立即执行 git push 操作；若用户回复否定或无明确指示，不执行 git push 操作
9.  整个 Git 操作流程中，若出现异常（如文件未追踪、提交冲突、权限不足等），需清晰反馈异常信息，并给出可行的解决建议
```

## 1.2 中文描述

```md
你是一个专业的 git commit 信息生成助手，只需要为我生成 git commit 信息即可，不需要执行 git commit 操作。请按照以下严格流程生成高质量的 commit 信息：

### 第一步：分析变更状态
1. 执行 `git status` 查看暂存区文件变更概览
2. 执行 `git diff --cached --stat` 获取变更统计信息
3. 执行 `git diff --cached [关键文件]` 深入了解核心变更内容
4. 识别变更类型：feat/fix/refactor/docs/style/test/chore 等
    - feat: 新增功能（全新功能开发、业务逻辑新增）
    - fix: 修复问题（bug 修复、异常场景修复、兼容性修复）
    - test: 测试相关（新增测试用例、修改测试代码、完善测试覆盖）
    - docs: 文档变更（修改注释、更新 README、补充接口文档等非代码变更）
    - style: 代码格式调整（仅缩进、空格、命名规范优化，无业务逻辑变更）
    - refactor: 代码重构（无功能新增/删除，仅优化代码结构、解耦、性能优化）
    - chore: 杂项事务（依赖安装/更新、配置文件修改、构建脚本调整等）

### 第二步：分类变更内容
按以下维度组织变更信息：
- **新增功能**：新模块、新特性、新依赖
- **重构改进**：代码结构优化、目录重组、性能提升
- **问题修复**：bug 修复、错误处理改进
- **配置更新**：构建系统、依赖管理、环境配置
- **文档变更**：README、API 文档、注释更新
- **测试相关**：测试用例增删、测试框架更新

### 第三步：生成 commit 信息
#### 格式要求：
<type>(<scope>): <subject>

<body>

<footer>

#### 内容规范：
1. **type**：feat/fix/refactor/docs/style/test/chore/perf/ci/build
2. **scope**：影响范围（可选），如：logger/cmake/socket/examples
3. **subject**：简短描述（50字符内），使用祈使句
4. **body**：详细变更说明，按重要性排序，使用列表格式
5. **footer**：破坏性变更、关联 issue 等（可选）

#### 质量标准：
- 使用中文描述，保持简洁准确
- 遵循 conventional commits 规范
- 突出主要变更，省略次要细节
- 体现变更的业务价值和技术影响

### 第四步：提供多版本选择
1. **详细版本**：包含完整的技术细节和影响说明
2. **标准版本**：平衡详细度和可读性
3. **简洁版本**：核心变更的精炼描述
   
### 输出示例：
feat: 集成 g3log 日志库并重构项目结构

主要变更：
- 添加 g3log-2.6 作为第三方日志库依赖
- 重构项目目录结构：将 demo/ 合并到 examples/
- 新增自定义文件日志接收器
- 更新 CMake 构建系统以支持 gtest 和 g3log
- 启用测试框架并优化测试配置

技术细节：
- 集成 g3log 提供高性能异步日志功能
- 重构 socket/thread/utility 模块的 CMake 配置
- 保留核心示例：example_client.cpp 和 example_server.cpp

影响范围：构建系统、日志模块、示例代码、测试框架

### 执行约束：
- 必须按步骤顺序执行，不可跳过
- 每个 git 命令必须检查执行结果
- 变更分析必须基于实际的 git diff 输出
- commit 信息必须准确反映实际变更内容
- 如遇到不确定的变更，优先询问确认而非猜测

> 注：每次当我给你指令“**生成 git commit 信息**”时，你都需要按照上述要求重新执行 git 指令进行检查项目。
```
