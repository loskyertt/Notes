> [!abstract]
> **线程（Thread）** 是程序执行的最小单位。C++11 引入了标准库 `<thread>`，让我们可以更方便地编写多线程代码。
> 这里面的很多概念其实会涉及到 [操作系统](../../操作系统/readme.md) 的知识点，如果之前学过操作系统中 **进程与线程** 的概念，那么涉及编程语言的多线程或多进程编程的概念，理解起来会轻松很多。

# 1. 线程与进程

## 1.1 基本概念

### 1.1.1 进程（Process）

进程是操作系统进行**资源分配的基本单位**。每个进程拥有独立的虚拟地址空间、文件描述符表、信号处理表等系统资源。操作系统通过进程控制块（PCB，Process Control Block）来描述和管理进程的状态信息。

进程的独立性是一把双刃剑：它提供了**强隔离性**（一个进程崩溃通常不会影响其他进程），但也使得进程间通信（IPC）的代价相对较高，需要借助管道、消息队列、共享内存、套接字等机制。

### 1.1.2 线程（Thread）

线程是操作系统进行**调度执行的基本单位**，也称为轻量级进程（LWP，Light Weight Process）。在 Linux 内核中，线程的本质仍是进程——内核使用同一个数据结构（`task_struct`）描述进程和线程，二者的核心区别在于：**线程通过 `clone()` 系统调用创建，并与父进程共享地址空间和部分资源，而非像 `fork()` 那样完整复制**。

## 1.2 进程与线程的资源模型

理解线程与进程的关系，关键在于弄清楚哪些资源是独占的，哪些是共享的。

### 1.2.1 线程独享的资源

即便是在同一进程的地址空间内，每个线程也拥有属于自己的私有状态：

|资源|说明|
|---|---|
|**栈空间**|每个线程有独立的调用栈，用于存放局部变量、函数调用帧和返回地址，默认大小通常为 8MB（Linux）|
|**程序计数器（PC）**|记录当前线程的执行位置，是线程独立调度的基础|
|**寄存器组**|包括通用寄存器、栈指针（SP）、帧指针（FP）等，构成线程的执行上下文，保存于内核中|
|**线程 ID（TID）**|在内核层面唯一标识一个线程|
|**信号掩码**|每个线程可独立设置屏蔽哪些信号|
|**`errno` 变量**|线程局部存储（TLS）实现，保证各线程的错误码互不干扰|

### 1.2.2 线程共享的资源

同一进程内的所有线程共享以下资源，这是多线程编程需要同步机制的根本原因：

|资源|说明|
|---|---|
|**代码段（Text Segment）**|程序的可执行指令，所有线程执行同一份代码|
|**数据段（Data Segment）**|已初始化的全局变量和静态变量|
|**BSS 段**|未初始化的全局变量|
|**堆（Heap）**|动态分配的内存（`malloc`/`new`），需注意线程安全|
|**文件描述符表**|打开的文件、套接字等，一个线程关闭文件描述符会影响所有线程|
|**信号处理函数**|通过 `signal`/`sigaction` 设置的处理函数是进程级别的|
|**进程 ID（PID）**|对外呈现为同一个进程|
|**虚拟地址空间**|内存映射（`mmap`）区域、共享库等|

## 1.3 上下文切换

> [!note]
> 上下文切换（Context Switch）是指 CPU 从一个执行单元切换到另一个时，**保存当前状态并恢复目标状态**的过程。其代价直接影响系统的整体性能。

**进程上下文切换**涉及：

1. 保存/恢复完整的寄存器组（包括浮点和向量寄存器）
2. 切换虚拟地址空间，即更换页表基址寄存器（如 x86 的 `CR3`）
3. **TLB（Translation Lookaside Buffer）失效**：地址空间切换后，TLB 中缓存的虚拟地址到物理地址的映射全部作废，后续内存访问需重新走页表查询，这是进程切换最主要的隐性开销之一
4. 切换内核栈、文件描述符表等进程级资源的引用

**线程上下文切换**仅涉及：

1. 保存/恢复寄存器组
2. 切换内核栈和线程私有状态

> [!important]
> 由于同一进程内的线程**共享地址空间，无需切换页表，TLB 仍然有效**，切换开销显著低于进程切换，这是线程相较于进程的核心性能优势。

## 1.4 多线程的优势

相比多进程的优势：
- **创建和销毁代价低**：线程无需复制父进程的地址空间（写时复制虽然缓解了 `fork()` 的即时开销，但仍有额外的内存管理代价），启动速度更快。
- **通信效率高**：线程间共享内存，数据交换无需序列化，避免了 IPC 的开销。
- **资源占用少**：多个线程复用同一地址空间和文件描述符表，系统开销更低。

> [!bug]
> 但是多线程并非没有代价。共享内存在带来效率的同时也引入了风险：一个线程的野指针写入、栈溢出等错误可能破坏整个进程的内存状态，导致其他线程一并崩溃。对于需要强隔离性的场景（如浏览器的多标签页、微服务架构），多进程模型反而更为合适。

## 1.5 线程数量的合理设置

线程并非越多越好。线程数超过一定阈值后，上下文切换的开销会抵消并发带来的收益，甚至导致性能下降。合理的线程数取决于任务的性质：

1. **CPU 密集型任务**

任务主要消耗 CPU 进行计算（如图像处理、加密运算、科学计算），线程在运行期间几乎不等待外部资源，此时：

$$N_{threads} = N_{CPU cores}$$

超出核心数的线程只会增加无谓的上下文切换，降低 CPU 利用率。

2. **I/O 密集型任务**

任务大量时间阻塞在 I/O 等待上（如网络请求、磁盘读写、数据库查询），CPU 在等待期间是空闲的，可以切换到其他线程执行，此时可以配置更多线程：

$$N_{threads} = N_{CPU cores} \times (1 + \frac{T_{wait}}{T_{compute}})$$

其中 $T_{wait}$ 是单次 I/O 等待时间，$T_{compute}$ 是 CPU 实际计算时间。当二者比值为 1 时（即各占一半），线程数约为核心数的 2 倍，这也是经验公式 $2 \times N_{CPU cores}$ 的理论依据。

> [!tip] 实践建议
> 理论公式提供了起点，但最优线程数受 **业务逻辑、锁竞争程度、内存压力** 等多因素影响，最终应通过 **基准测试（Benchmark）和性能分析（Profiling）** 在目标环境中实测确定，而非仅凭公式推算。

## 1.6 线程的调度

线程调度中主要有三种状态：

| 状态 | 是否占用 CPU | 是否在调度队列 | 能否立即运行 | 位于内存？ |
|---|---|---|---|---|
| **就绪态** | ❌ | ✅ 在 | ✅ 等待 CPU | ✅ 在 |
| **运行态** | ✅ | ✅ 在 | ✅ 正在运行 | ✅ 在 |
| **阻塞态** | ❌ | ❌ 不在 | ❌ 必须等条件，条件满足先转为就绪态，再由 CPU 调度 | ✅ 在 |

**三种状态下线程的栈、寄存器上下文等数据始终保留在内存中**，所谓“挂起”只是**从调度队列中移除**，并不是移出内存。将线程移出内存是操作系统的**内存换页**行为，与线程状态管理是两个独立的机制。

> [!note] 就绪态和阻塞态的核心区别在于：
> - **就绪态**：万事俱备，只欠 CPU
> - **阻塞态**：条件未满足，给我 CPU 也没用，先别调度我

# 2. thread 线程类详解

C++11 之前，C++ 语言本身不提供任何并发支持，开发者只能依赖平台相关的 API（如 POSIX 的 `pthread`、Windows 的 `CreateThread`），导致多线程代码无法跨平台移植。

C++11 将线程支持纳入标准库，提供了 `std::thread` 及配套的同步原语（`mutex`、`condition_variable`、`atomic` 等），使得多线程程序的编写首次做到了**语言级别的可移植性**。使用时需包含头文件 `<thread>`，并在编译时链接线程库（GCC/Clang 使用 `-pthread` 选项）。

## 2.1 构造函数

```cpp
// ① 默认构造：不关联任何线程
thread() noexcept;

// ② 移动构造：转移线程所有权
thread(thread&& other) noexcept;

// ③ 创建并启动线程
template<class Function, class... Args>
explicit thread(Function&& f, Args&&... args);

// ④ 禁止拷贝
thread(const thread&) = delete;
```

1. **默认构造**：创建一个**不代表任何执行线程**的空 `thread` 对象，`joinable()` 返回 `false`，通常用作占位或后续通过移动赋值填充。
2. **移动构造**：移动语义转移线程所有权。转移后，`other` 变为空对象，不再关联任何线程。`std::thread` 与其管理的系统线程之间是**独占所有权**关系，这正是拷贝构造被删除的原因。
3. **创建并启动线程**：最常用的形式。线程对象构造完成的同时，操作系统线程即被创建并开始执行。
4. **拷贝构造**：`=delete` 显式禁止拷贝，系统线程资源无法被复制，这是所有权语义的基础。

### 2.1.1 线程的创建

> 一般是采用第三种构造函数进行创建。

创建一个线程非常简单：实例化一个 `std::thread` 对象，并给它一个函数作为任务。

```cpp
#include <iostream>
#include <thread>

void printHello(std::string name) {
    std::cout << "你好, " << name << "！来自线程 ID: " 
              << std::this_thread::get_id() << std::endl;
}

int main() {
    // 1. 创建并启动线程
    std::thread t1(printHello, "工人 A");
    
    // 2. 主线程继续做事
    std::cout << "主线程正在忙碌..." << std::endl;

    // 3. 主线程在这里停下，等待 t1 彻底干完活再继续
    // 如果不 join，主线程结束时子线程会被强制杀死导致崩溃
    t1.join();

    std::cout << "所有任务完成。" << std::endl;
    return 0;
}
```

> `std::thread` 构造成功后，新线程会被创建并进入“可运行（runnable）状态”，通常会被放入调度器的**就绪队列**，等待 CPU 调度。

你可以直接通过 `std::thread` 的构造函数传递参数，它支持传递值、引用或 Lambda 表达式：

```cpp
void PrintMessage(int id, std::string msg) {
    std::cout << "线程 " << id << ": " << msg << "\n";
}

int main() {
    std::string text = "加油写代码";
    
    // 传递参数：id = 1, msg = text
    std::thread t1(PrintMessage, 1, text);
    
    // 使用 Lambda 表达式启动线程（最常用）
    std::thread t2([&]() {
        std::cout << "Lambda 线程正在运行...\n";
    });

    t1.join();
    t2.join();
}
```

> `std::thread` 的构造函数其实使用了 **可变参数模板**。它会把参数**拷贝**到线程的独立内存空间中。

`Function` 可以是普通函数、类成员函数、lambda、仿函数、`std::function`，以及经 `std::bind` 绑定后的可调用对象。传入类成员函数时，需同时传入**对象指针**或**引用**：

```cpp
struct Worker {
    void run(int n) { /* ... */ }
};

Worker w;
std::thread t(&Worker::run, &w, 42);  // 传入成员函数指针 + 对象指针 + 参数
```

**注意点**：参数默认以**值拷贝**方式传入线程，如果你想传递 **引用**，直接写 `&x` 是无效的（编译器会报错或依然按值拷贝）。必须使用 `std::ref()`。

```cpp
void increment(int& val) { val++; }

int x = 0;
std::thread t1(increment, x);          // ❌ 传的是 x 的副本，x 不变
std::thread t2(increment, std::ref(x)); // ✅ 传引用，x 会被修改
```

## 2.2 公共成员函数

### 2.2.1 `get_id()`

```cpp
std::thread::id get_id() const noexcept;
```

返回当前线程对象关联的线程 ID，类型为 `std::thread::id`。每个运行中的线程拥有全局唯一的 ID，可用于日志记录、调试和线程标识。

- 对未关联任何线程的对象调用 `get_id()`，返回默认构造的 `std::thread::id`（代表"无线程"）。
- 获取**当前执行线程**自身的 ID，应通过命名空间函数 `std::this_thread::get_id()`，而非通过线程对象。

```cpp
std::thread t([] {
    // 在子线程内部获取自身 ID
    auto tid = std::this_thread::get_id();
});
// 在主线程通过对象获取子线程 ID
std::cout << t.get_id() << "\n";
t.join();
```

### 2.2.2 `join()`

`join()` 字面意思是连接一个线程，意味着**主动地等待线程的终止**。在某个线程中通过子线程对象调用 `join()` 函数，**调用这个函数的线程被阻塞**，但是子线程对象中的任务函数会继续执行，当任务执行完毕之后 `join()` 会**清理当前子线程中的相关资源**（比如线程持有的文件描述符）然后返回，同时，调用该函数的线程解除阻塞继续向下执行。

```cpp
void join();
```

再次强调，我们一定要搞清楚这个函数阻塞的是哪一个线程：**函数在哪个线程中被执行，那么函数就阻塞哪个线程**。被 `join()` 的线程结束后，其占用的系统资源（内核栈、调度信息等）会随 `join()` 的返回而被回收，**此后 `joinable()` 返回 `false`**。

```cpp
void doWork(){
  std::println("做一些事 ....");
}

void test() {
  std::thread t(doWork);
  t.join();
}
```

> 比如上面这段代码示例：**调用 `test()` 的线程**就是调用 `join()` 的线程（因为 `join()` 在 `test()` 中），所以调用 `test()` 的线程被阻塞；而 `t` 线程就是被 `join()` 的线程，它会做自己的事，做完后，就把已持有的资源释放掉。

关键细节：

- **阻塞的是调用者**：`t.join()` 写在哪个线程中，哪个线程就会被阻塞。通常是主线程调用，因此主线程阻塞等待子线程。
- **不可重复调用**：`join()` 之后线程已不处于 joinable 状态，再次调用会抛出 `std::system_error`。
- **任务已完成时不阻塞**：若调用 `join()` 时子线程已经执行完毕，主线程不会等待，立即返回。

> [!example]
> 为了更好的理解 `join()` 的使用，再来举一个例子，场景如下：
> 程序中一共有三个线程，其中两个子线程负责分段下载同一个文件，下载完毕之后，由主线程对这个文件进行下一步处理。

根据场景设定，那么示例程序就应该这么写：

```cpp
#include <print>
#include <thread>
#include <chrono>

void download1() {
  // 模拟下载, 总共耗时500ms，阻塞线程500ms
  std::this_thread::sleep_for(std::chrono::milliseconds(500));
  std::println("子线程1: {}, 找到历史正文....", std::this_thread::get_id());
}

void download2() {
  // 模拟下载, 总共耗时300ms，阻塞线程300ms
  std::this_thread::sleep_for(std::chrono::milliseconds(300));
  std::println("子线程2: {}, 找到历史正文....", std::this_thread::get_id());
}

void doSomething() {
  std::println("集齐历史正文, 呼叫罗宾....");
  std::println("历史正文解析中....");
  std::println("起航，前往拉夫德尔....");
  std::println("找到OnePiece, 成为海贼王, 哈哈哈!!!");
  std::println("若干年后，草帽全员卒....");
  std::println("大海贼时代再次被开启....");
}

int main() {
  std::thread t1(download1);
  std::thread t2(download2);
  // 阻塞主线程，等待所有子线程任务执行完毕再继续向下执行
  t1.join();
  t2.join();
  doSomething();
}
```

输出结果：

```bash
子线程2: 4036, 找到历史正文....
子线程1: 11424, 找到历史正文....
集齐历史正文, 呼叫罗宾....
历史正文解析中....
起航，前往拉夫德尔....
找到OnePiece, 成为海贼王, 哈哈哈!!!
若干年后，草帽全员卒....
大海贼时代再次被开启....
```

在上面示例程序中最核心的处理是在主线程调用 `doSomething()` 之前就通过子线程对象调用了 `join()` 方法，这样就能够保证两个子线程的任务都执行完毕了，也就是文件内容已经全部下载完成，**主线程**（即调用 main 函数的这个线程）再对文件进行后续处理。如果子线程的文件没有下载完毕，主线程就去处理文件，很显然从逻辑上讲是有问题的。

### 2.2.3 `detach()`

```cpp
void detach();
```

**语义**：将线程对象与底层系统线程分离。分离后，系统线程独立运行，任务结束时自动释放资源；线程对象本身变为空，`joinable()` 返回 `false`，此后不能再对其调用 `join()` 或 `detach()`。

```cpp
#include <thread>
#include <print>

void func(int num, std::string str) {
  for (int i = 0; i < 10; ++i) {
    std::println("子线程: i = {}, num: {}, str: {}", i, num, str);
  }
}

void func1() {
  for (int i = 0; i < 10; ++i) {
    std::println("子线程: i = {}", i);
  }
}

int main() {
  std::println("主线程的线程 ID: {}", std::this_thread::get_id());
  std::thread t1(func, 520, "i love you");
  std::thread t2(func1);
  std::println("线程 t1 的线程 ID: {}", t1.get_id());
  std::println("线程 t2 的线程 ID: {}", t2.get_id());

  t1.detach();
  t2.detach();
  // 让主线程休眠, 等待子线程执行完毕
  std::this_thread::sleep_for(std::chrono::seconds(5));
}
```

注意事项：

- `detach()` **不会阻塞**调用线程，调用后立即返回。
- `main()` 函数返回后，所有仍在运行的 detached 线程会被操作系统**强制终止**，不执行析构或资源清理。因此若 detached 线程中有写文件、释放锁等操作，需要额外的生命周期管理手段（如全局信号量）来保证程序退出前任务已完成。
- detached 线程访问的数据必须保证在线程运行期间的有效性，推荐通过 `std::shared_ptr` 管理共享数据，而非裸引用或裸指针指向栈上变量。

### 2.2.4 `joinable()`

```cpp
bool joinable() const noexcept;
```

用于查询线程对象是否关联一个活跃的系统线程（即当前处于可 join 状态）。在调用 `join()` 或 `detach()` 之前应先检查 `joinable()`，以避免对空线程或已分离线程的误操作：

```cpp
void safe_join(std::thread& t) {
    if (t.joinable()) {
        t.join();
    }
}
```

以下情况 `joinable()` 返回 `false`：

|情形|原因|
|---|---|
|默认构造的 `thread` 对象|未关联任何线程|
|调用 `join()` 之后|线程已结束，资源已回收|
|调用 `detach()` 之后|线程对象与系统线程已解除绑定|
|被移动后的 `thread` 对象|所有权已转移给其他对象|

示例：

```cpp
#include <print>
#include <thread>
#include <chrono>

void foo() {
  std::this_thread::sleep_for(std::chrono::seconds(1));
}

int main() {
  std::thread t;
  std::println("before starting, joinable: {}", t.joinable());

  t = std::thread(foo);
  std::println("after starting, joinable: {}", t.joinable());

  t.join();
  std::println("after joining, joinable: {}", t.joinable());

  std::thread t1(foo);
  std::println("after starting, joinable: {}", t1.joinable());
  t1.detach();
  std::println("after detaching, joinable: {}", t1.joinable());
}
```

输出：

```bash
before starting, joinable: false
after starting, joinable: true
after joining, joinable: false
after starting, joinable: true
after detaching, joinable: false
```

基于示例代码打印的结果可以得到以下结论：
- 在创建的子线程对象的时候，如果**没有指定任务函数**，那么子线程不会启动，主线程和这个子线程也不会进行连接。
- 在创建的子线程对象的时候，如果指定了任务函数，子线程启动并执行任务，主线程和这个子线程自动连接成功。
- 子线程调用了 `detach()` 函数之后，父子线程分离，同时二者的连接断开，调用 `joinable()` 返回 `false`。
- 在子线程调用了 `join()` 函数，子线程中的任务函数继续执行，直到任务处理完毕，这时 `join()` 会清理（回收）当前子线程的相关资源，所以这个子线程和主线程的连接也就断开了，因此，调用 `join()` 之后再调用 `joinable()` 会返回 `false`。

### 2.2.5 `operator=`

```cpp
thread& operator=(thread&& other) noexcept;  // 移动赋值
thread& operator=(const thread&) = delete;   // 禁止拷贝赋值
```

通过以上 `=` 操作符的重载声明可以得知：
- 如果 `other` 是一个**右值**，会进行资源所有权的转移；
- 如果 `other` 不是右值，禁止拷贝，该函数被显示删除（=delete），不可用。

移动赋值会接管 `other` 的线程所有权。需注意：**若赋值目标本身已关联一个 joinable 的线程，移动赋值会调用 `std::terminate()`**，因此赋值前应确保目标对象处于非 joinable 状态：

```cpp
std::thread t1(task_a);
std::thread t2(task_b);

// ❌ 危险：t1 仍处于 joinable 状态，此赋值会触发 std::terminate()
t1 = std::move(t2);

// ✅ 正确：先处理 t1，再赋值
t1.join();
t1 = std::move(t2);
```

## 2.3 静态成员函数

### 2.3.1 `hardware_concurrency()`

```cpp
static unsigned hardware_concurrency() noexcept;
```

返回当前硬件支持的**并发线程数**，通常等于逻辑 CPU 核心数（包含超线程）。这一值可作为创建 CPU 密集型线程池时的线程数参考。

```cpp
#include <print>
#include <thread>

int main() {
  std::size_t num = std::thread::hardware_concurrency();
  std::println("CPU number: {}", num);
}
```

输出：

```bash
CPU number: 12
```

注意该函数返回的是**建议值**而非硬性限制：

- 若无法获取（某些嵌入式平台），返回 `0`，调用方应做好处理。
- 对于 I/O 密集型任务，最优线程数通常高于此值，不应将其作为唯一依据。

```cpp
unsigned int n = std::thread::hardware_concurrency();
size_t thread_count = (n > 0) ? n : 4;  // 获取失败时使用默认值
```

# 3. `this_thread` 命名空间

标准库在 `std::this_thread` 命名空间下提供了一组作用于**当前线程**的工具函数：

|函数|说明|
|---|---|
|`std::this_thread::get_id()`|获取当前线程 ID|
|`std::this_thread::sleep_for(duration)`|**阻塞**当前线程指定时长（线程从“运行态 -> 阻塞态”）|
|`std::this_thread::sleep_until(time_point)`|**阻塞**当前线程至指定时间点（线程从“运行态 -> 阻塞态”）|
|`std::this_thread::yield()`|主动**让出 CPU 时间片**，提示调度器切换至其他线程（线程从“运行态 -> 就绪态”）|

`yield()` 常用于自旋等待场景，避免忙等时持续占用 CPU：

```cpp
while (!flag.load()) {
    std::this_thread::yield();  // 让出 CPU，等待 flag 被其他线程置为 true
}
```

# 4. 线程对象的生命周期管理原则

`std::thread` 对象析构时，若仍处于 joinable 状态（既未 `join` 也未 `detach`），标准库会调用 `std::terminate()` 终止整个程序。因此每个线程对象在其析构之前，必须明确完成以下其中之一：

```
创建线程对象
     ↓
  确定策略
  ↙       ↘
join()   detach()
需等待结果  完全独立
或访问共享  fire-and-forget
局部变量
```

为避免异常路径导致的 `terminate`，推荐使用 RAII 封装，在析构函数中自动处理：

```cpp
class ScopedThread {
    std::thread t_;
public:
    explicit ScopedThread(std::thread t) : t_(std::move(t)) {
        if (!t_.joinable())
            throw std::logic_error("No thread");
    }
    ~ScopedThread() {
        t_.join();  // 析构时自动 join，保证资源安全回收
    }
    ScopedThread(const ScopedThread&) = delete;
    ScopedThread& operator=(const ScopedThread&) = delete;
};
```

C++20 引入的 `std::jthread` 已将上述 RAII 语义内置：析构时自动请求停止并 join，是新代码的优先选择。

# 5. join 和 detach 的适用场景

线程的两个核心动作：`join` 与 `detach`。当你启动一个线程后，你必须在 `std::thread` 对象**销毁前**决定如何处理它，否则程序会直接崩溃（调用 `std::terminate`）。

比如 [2.1.1 线程的创建](###\ 2.1.1\ 线程的创建) 的代码示例，如果**没有 `t1.join(); `**，`main` 函数运行得很快，当它执行到 `return 0` 时，子线程 `t1` 还处于阻塞（Blocked）或休眠（Sleeping）状态。此时 `t1` 对象被析构，但它代表的线程还在运行。C++ 标准认为这是一种极其危险的行为，会直接调用 `std::terminate()` 杀掉整个程序。

- **`join()` (汇合)**：主线程会停下来，**等待**子线程执行完毕。
- **`detach()` (分离)**：主线程与子线程彻底分离（比如让子线程在后台独立运行），各自独立运行，主线程不再管它。

这两者都是为了解决同一个问题：**`std::thread` 对象析构时，若线程仍处于 joinable 状态，程序会直接调用 `std::terminate()` 崩溃**。因此每个线程必须明确选择其中之一。

> 如果使用 `detach()`，子线程可能会在主函数结束后继续运行。如果子线程访问了主线程中已经销毁的局部变量（比如引用或指针），会导致 **非法内存访问**。因此，除非是守护进程类的任务，否则 **优先使用 `join()`**。

## 5.1 join

由于 `join()` 需要等待结果或保证完成，故有以下适用场景：

1. **依赖子线程的计算结果**

```cpp
std::vector<int> result;
std::thread worker([&result] {
    result = compute_heavy_task();  // 耗时计算
});

// 主线程做其他事...
do_something_else();

worker.join();  // 必须等 worker 完成，才能安全使用 result
process(result);
```

2. **子线程访问主线程的局部变量**

这是最常见的 `join` 必用场景。若主线程先退出，子线程访问的局部变量已被销毁，产生悬空引用：

```cpp
void foo() {
    int local_data = 42;
    std::thread t([&local_data] {
        std::this_thread::sleep_for(std::chrono::seconds(1));
        std::cout << local_data;  // 若 foo 已返回，local_data 已销毁！
    });
    t.join();  // 必须 join，确保 t 退出前 foo 不返回
}
```

3. **需要顺序保证的阶段性任务**

```cpp
std::thread stage1(load_data);
stage1.join();   // 第一阶段必须完成

std::thread stage2(process_data);
stage2.join();   // 第二阶段必须完成

std::thread stage3(save_result);
stage3.join();
```

4. **线程池的优雅关闭**

线程池析构时，需等待所有工作线程耗尽任务队列后退出：

```cpp
~ThreadPool() {
    stop_ = true;
    cv_.notify_all();
    for (auto& t : workers_) {
        if (t.joinable()) t.join();  // 等待每个工作线程自然退出
    }
}
```

## 5.2 detach

`detach()` 有以下适用场景：

1. **后台守护任务**

任务与主流程无关，**生命周期可以超过创建它的函数**：

```cpp
void start_monitor() {
    std::thread t([] {
        while (true) {
            collect_metrics();
            std::this_thread::sleep_for(std::chrono::seconds(10));
        }
    });
    t.detach();  // 监控线程独立运行，无需等待
}
```

2. **日志、审计等旁路任务**

```cpp
void on_user_login(User user) {
    std::thread([user] {
        write_audit_log(user);   // 写日志不影响主流程
    }).detach();

    redirect_to_dashboard(user);  // 立即响应用户
}
```

3. **线程自身管理自身生命周期**

任务完成后线程自然退出，无需外部干预：

```cpp
void handle_client(Socket socket) {
    std::thread([s = std::move(socket)] {
        process_request(s);
        // 函数返回，线程自动退出
    }).detach();
}
```

## 5.3 补充

`detach` 看似方便，但使用不当极易引发未定义行为，需格外谨慎。

**风险一：访问已销毁的局部变量**

```cpp
void dangerous() {
    int local = 42;
    std::thread([&local] {        // 捕获局部变量引用
        std::this_thread::sleep_for(std::chrono::seconds(1));
        std::cout << local;       // ❌ dangerous() 早已返回，local 已销毁
    }).detach();
}   // 函数返回后，local 销毁，线程仍在运行
```

**风险二：主进程退出时线程被强制终止**

`main()` 返回后，所有 detached 线程会被直接杀死，不会执行析构或清理：

```cpp
int main() {
    std::thread([] {
        prepare_data();
        save_to_disk();     // ❌ 可能在写到一半时被强制终止
    }).detach();
    return 0;               // main 退出，线程戛然而止
}
```

**避免方式**：detached 线程只应使用堆上分配的数据（通过 `shared_ptr` 共享所有权），而不是引用/指针指向栈上变量。如下：

```cpp
void safe_detach() {
    auto data = std::make_shared<MyData>();  // 堆上，引用计数保护
    std::thread([data] {                     // 值捕获 shared_ptr
        process(*data);
    }).detach();
}   // data 的引用计数由线程持有，不会提前销毁
```

因此，在实际开发中，可以根据下面几个问题来进行决策：

```
子线程访问了主线程的局部变量？          → 必须 join
需要子线程的返回值或需确认完成？        → 必须 join（或用 std::future）
任务是后台守护、日志等旁路任务？        → 可以 detach
任务生命周期需超过创建它的函数？        → 可以 detach，但必须用 shared_ptr 管理共享数据
```

> [!tip] 更现代的替代方案
> 实践中，裸用 `detach` 已较少推荐。更安全的替代方案是：
> - **需要结果**：用 `std::async` + `std::future`，自动管理生命周期。
> - **需要后台任务**：用线程池提交任务，由线程池统一管理线程生命周期，避免手动 `detach` 的风险。
