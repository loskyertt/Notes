# 1. 多线程并发存在的问题

多个线程共享同一进程的地址空间，这在带来通信便利的同时，也引入了**数据竞争（Data Race）** 的风险。当以下三个条件同时成立时，数据竞争就会发生：

1. 两个或更多线程并发访问同一块内存
2. 其中至少有一个线程在执行**写操作**
3. 没有任何同步机制加以保护

数据竞争属于**未定义行为（Undefined Behavior）**，其后果不可预测：程序可能得到错误的计算结果，也可能在某些运行中表现正常而在另一些运行中崩溃，这类 bug 往往极难复现和定位。

> [!note]
> 简单来说：由于操作系统 **异步性** 的特征和线程 **并发性** 的特点，线程以何种速度运行是不可预知的，就会造成**资源竞争** (Race Condition)的现象。因此当多个线程**同时修改同一个变量**时，就会出现问题。

错误示范：

```cpp
#include <print>
#include <thread>

static int counter = 0;

void increase(int times) {
  for (int i = 0; i < times; ++i) {
    counter++;  // ⚠️ 非原子操作：读取、加一、写入，中间可能被切换
  }
}

int main() {
  std::thread t1(increase, 100000);
  std::thread t2(increase, 100000);
  t1.join();
  t2.join();
  std::println("Counter: {}", counter);  // 结果通常小于 200000，因为两个线程互相覆盖了对方的结果
}
```

第一次运行时的输出：

```bash
Counter: 104377
```

第二次运行时的输出：

```bash
Counter: 101081
```

`counter++` 在 CPU 层面并非原子操作，而是三条独立指令：

```
① LOAD  : 将 counter 的值从内存读入寄存器
② ADD   : 寄存器中的值加 1
③ STORE : 将寄存器中的值写回内存
```

若两个线程同时执行，可能出现以下交错（counter 初始值为 0）：

```
线程 A               线程 B
LOAD  → 读到 0
                     LOAD  → 读到 0
ADD   → 得到 1
STORE → 写入 1
                     ADD   → 得到 1
                     STORE → 写入 1   ← 期望写入 2，实际写入 1
```

两次自增操作，counter 却只增加了 1，这就是**丢失更新（Lost Update）**，是数据竞争最典型的表现形式之一。

# 2. 同步

## 2.1 基本概念

**线程同步（Thread Synchronization）** 是指通过特定机制，协调多个线程对共享资源的访问顺序，确保在任意时刻对共享资源的操作满足预期的一致性约束。

> 需要特别强调的是：**“同步”并不意味着“同时”**。恰恰相反，同步的本质是**串行化**——让多个线程对共享资源的访问有序地依次进行，而非并行交错。

以 A、B、C、D 四个线程并发访问同一块共享内存为例，在同步机制的保护下，其访问过程如下：

```
时间轴 ──────────────────────────────────────────────────►

线程 A  ████████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░  (执行完毕，释放)
线程 B  ░░░░░░░░░░░░████████░░░░░░░░░░░░░░░░░░░░░░  (等待 A → 执行 → 释放)
线程 C  ░░░░░░░░░░░░░░░░░░░░████░░░░░░░░░░░░░░░░░░  (等待 B → 执行 → 释放)
线程 D  ░░░░░░░░░░░░░░░░░░░░░░░░░░░░████████░░░░░░  (等待 C → 执行 → 释放)

        ████ 占用资源中    ░░░░ 阻塞等待中
```

任意时刻最多只有一个线程处于访问状态，其余线程处于等待状态，直到当前线程完成访问并"释放"资源后，等待中的某一个线程才能获得访问权。

**与线程同步相关的核心概念**：
- **共享资源（Shared Resource）**：被多个线程/进程同时访问的资源。例如：全局变量、堆上的对象、文件描述符（`socket` / `fd`）、数据结构（`std::vector`, `std::map`）。
- **临界资源（Critical Resource）**：在某一时刻**只能被一个线程安全访问的共享资源**。如果并发访问就可能出错，因此访问必须**互斥**。

> [!warning]
> 一定要区分这两个概念：
> - 如果你把“所有共享资源都当临界资源”，就会因为**过度加锁**导致性能下降，并且降低代码的扩展性。
> - 如果你把“临界资源当普通共享资源”，就会造成**数据竞争**（data race）和**未定义行为**（UB），严重的话会导致程序崩溃。

- **临界区（Critical Section）**：程序中**访问临界资源**的那段**代码**区域。任何时刻，**最多只允许一个线程在临界区内执行**。比如：

```cpp
std::mutex mtx;

void f() {
    std::lock_guard<std::mutex> lock(mtx);  // 临界区开始

    counter++;  // 对临界资源的访问

} // 临界区结束
```

- **互斥（Mutual Exclusion）**：保证临界区同一时刻只有一个线程执行的性质，是实现线程同步的核心约束。

## 2.2 同步方式

对于多个线程访问共享资源出现数据混乱的问题，需要进行线程同步。常用的线程同步方式有四种：**互斥锁**、**读写锁**、**条件变量**、**信号量**。

线程同步的大致处理思路是这样的：
1. 在临界区代码的上边，添加加锁函数，**对临界区加锁**。
2. 哪个线程调用这句代码，就会把这把锁锁上，其他线程就只能阻塞在锁上了。
3. 在临界区代码的下边，添加解锁函数，对临界区解锁。
4. 出临界区的线程会将锁定的那把锁打开，其他抢到锁的线程就可以进入到临界区了。
5. 通过锁机制能保证临界区代码最多只能同时有一个线程访问，这样并行访问就变为串行访问了。

C++ 标准库提供了多种同步原语，适用于不同的场景：

| 机制 | 代表类型 | 核心用途 |
|---|---|---|
| **互斥锁** | `std::mutex` | 保护临界区，保证互斥访问 |
| **读写锁** | `std::shared_mutex` | 允许多个读者并发，写者独占 |
| **条件变量** | `std::condition_variable` | 线程间的等待/通知协调 |
| **原子操作** | `std::atomic` | 无锁保护单个变量的原子读写 |
| **信号量** | `std::counting_semaphore`（C++20） | 控制同时访问资源的线程数量 |
| **屏障** | `std::barrier`（C++20） | 让一组线程在某个点同步汇合 |

选择何种机制，需根据共享资源的访问模式、竞争强度和性能要求综合判断。接下来的章节将逐一介绍各种机制的原理与用法。

# 3. 互斥锁

## 3.1 使用方式

为了防止竞争，我们需要用一把“锁”（`lock()`）。同一时间，**只允许一个线程进入临界区**。对于普通的 `lock()`，操作系统会将阻塞的线程**挂起**（而非忙等），让出 CPU 给其他线程使用。当锁被释放时，操作系统负责唤醒其中一个等待线程，使其重新参与竞争。唤醒顺序通常由调度器决定，**标准库不保证公平性**——即不保证等待最久的线程优先获得锁，若有严格公平需求需自行实现队列机制。

通过以上机制，多个线程对临界区的并发访问被强制转化为串行访问：

```cpp
无锁（错误）：                    有锁（正确）：

线程A  ──██████──────────         线程A  ──[lock]██████[unlock]──────────────────
线程B  ────████████──────    →    线程B  ────────────────[lock]████████[unlock]───
线程C  ──────██████──────         线程C  ────────────────────────────────[lock]██████[unlock]

       并行交错，数据损坏                   串行执行，数据正确
```

## 3.2 死锁（Deadlock）

死锁是指两个或多个线程在执行过程中，因**互相等待对方释放资源**而陷入的永久阻塞状态。死锁一旦形成，涉及的线程既无法向前推进，也无法自行解除阻塞——因为唯一能解锁的线程自身也处于等待状态。

死锁的后果轻则导致部分功能丧失响应，重则使整个程序挂起，且由于死锁往往在特定的线程调度时序下才会触发，其复现和定位极为困难。

### 3.2.1 死锁的四个必要条件

1960 年，E.W. Dijkstra 提出了死锁成立的四个必要条件（Coffman 条件），**四者缺一不可**，破坏任意一个即可预防死锁：

1. **互斥条件（Mutual Exclusion）**
	资源在同一时刻只能被一个线程持有。互斥锁本身就满足这一条件，是使用锁的必然代价。

2. **持有并等待（Hold and Wait）**
	线程在持有至少一个资源的同时，等待获取其他线程占有的资源。

3. **不可抢占（No Preemption）**
	线程已获得的资源不能被强制剥夺，只能由持有者主动释放。

4. **循环等待（Circular Wait）**
	存在一个线程等待链，形成环路：线程 A 等待线程 B 持有的资源，线程 B 等待线程 C 持有的资源，……，最终某个线程等待线程 A 持有的资源。

### 3.2.2 典型的死锁场景

#### 场景一：两个线程、两把锁的经典死锁

```cpp
std::mutex lockA;
std::mutex lockB;

// 线程 1：先锁 A，再锁 B
void thread1() {
    lockA.lock();
    std::this_thread::sleep_for(std::chrono::milliseconds(1)); // 模拟时间窗口
    lockB.lock();   // ← 等待线程 2 释放 lockB，永远等不到
    // 临界区
    lockB.unlock();
    lockA.unlock();
}

// 线程 2：先锁 B，再锁 A
void thread2() {
    lockB.lock();
    std::this_thread::sleep_for(std::chrono::milliseconds(1)); // 模拟时间窗口
    lockA.lock();   // ← 等待线程 1 释放 lockA，永远等不到
    // 临界区
    lockA.unlock();
    lockB.unlock();
}
```

死锁形成的时序如下：

```
时间轴 ──────────────────────────────────────────────►

线程1   [lock A 成功]───────────────[lock B 阻塞，等待线程2]···
线程2   ───────[lock B 成功]───────[lock A 阻塞，等待线程1]···
```

**结果**：线程1 持有 A 等待 B，线程2 持有 B 等待 A，循环等待成立，双方永久阻塞。

#### 场景二：同一线程对同一非递归锁重复加锁

```cpp
std::mutex mtx;

void func() {
    mtx.lock();
    mtx.lock();   // ❌ 同一线程再次对非递归锁加锁，自己阻塞自己
    mtx.unlock();
    mtx.unlock();
}
```

`std::mutex` 是**非递归锁**，同一线程重复加锁会导致未定义行为（通常表现为立即死锁）。若确有递归加锁的需求，应使用 `std::recursive_mutex`。

#### 场景三：异常导致锁未释放，间接引发死锁

```cpp
std::mutex mtx;

void risky() {
    mtx.lock();
    process();      // 若此处抛出异常……
    mtx.unlock();   // ← 这行永远不会执行，锁泄漏
}

void other_thread() {
    mtx.lock();     // ← 永远无法获取锁，死锁
}
```

这是最隐蔽的死锁成因之一，必须通过 RAII 加以防范。

### 3.2.3 死锁的预防策略

#### 策略一：固定加锁顺序（破坏循环等待条件）

规定所有线程必须以**相同的顺序**获取锁，从根本上杜绝循环等待的形成：

```cpp
// 全局约定：总是先锁 A，再锁 B，无论哪个线程
void thread1() {
    lockA.lock();
    lockB.lock();
    // 临界区
    lockB.unlock();
    lockA.unlock();
}

void thread2() {
    lockA.lock();   // ✅ 与 thread1 加锁顺序一致
    lockB.lock();
    // 临界区
    lockB.unlock();
    lockA.unlock();
}
```

#### 策略二：使用 `std::scoped_lock` 同时加锁（C++17）

`std::scoped_lock` 内部采用死锁避免算法，可以**原子性地同时获取多个锁**，无论调用方以何种顺序传入，都不会产生死锁：

```cpp
// 无论两个线程参数顺序如何，都不会死锁
void thread1() {
    std::scoped_lock lock(lockA, lockB);  // 内部自动处理加锁顺序
    // 临界区
}   // 析构时自动按逆序释放

void thread2() {
    std::scoped_lock lock(lockB, lockA);  // 参数顺序不同，仍然安全
    // 临界区
}
```

在 C++17 之前，可以使用 `std::lock()` + `std::adopt_lock` 达到相同效果：

```cpp
std::lock(lockA, lockB);  // 原子性地同时获取两个锁
std::lock_guard<std::mutex> guardA(lockA, std::adopt_lock);
std::lock_guard<std::mutex> guardB(lockB, std::adopt_lock);
```

#### 策略三：使用 RAII 锁管理

始终使用 `std::lock_guard` 或 `std::unique_lock` 管理锁的生命周期，确保在任何执行路径下（包括异常）都能正确释放锁：

```cpp
void safe_func() {
    std::lock_guard<std::mutex> guard(mtx);  // 构造时加锁
    process();   // 即使此处抛出异常，guard 析构时也会自动解锁
}                // 作用域结束，自动解锁
```

#### 策略四：使用 `try_lock` 避免无限等待（破坏持有并等待条件）

尝试获取锁，若失败则**主动释放已持有的锁**并重试，避免持有资源同时无限期等待：

```cpp
void thread_func() {
    while (true) {
        lockA.lock();
        if (lockB.try_lock()) {     // 尝试获取 lockB
            break;                   // 成功，跳出循环进入临界区
        }
        lockA.unlock();              // 失败，释放已持有的 lockA，重试
        std::this_thread::yield();   // 让出 CPU，给其他线程机会
    }
    // 临界区：此时同时持有 lockA 和 lockB
    lockB.unlock();
    lockA.unlock();
}
```

注意这种方式可能导致**活锁（Livelock）**——两个线程反复同时获取第一把锁、尝试第二把锁失败、同时释放，如此循环，无法推进。可通过引入随机退避时间加以缓解：

```cpp
std::this_thread::sleep_for(
    std::chrono::milliseconds(rand() % 10)  // 随机等待，错开竞争时机
);
```

#### 策略五：减少锁的持有时间和数量

持有多把锁是死锁的前提，因此优化锁的设计本身是最根本的预防手段：

- 尽量缩小临界区范围，减少锁的持有时间
- 重新审视数据结构设计，减少需要同时持有多把锁的场景
- 对读多写少的场景，使用 `std::shared_mutex` 允许多个读者并发，减少锁竞争

### 3.2.4 死锁的检测与恢复

在无法完全避免死锁的系统中（如数据库），通常引入死锁检测机制：

**资源分配图（Resource Allocation Graph）**：维护一张线程与资源之间的有向图，若图中存在环路，则判定死锁成立。操作系统和数据库管理系统普遍采用此方法。

检测到死锁后的恢复策略：

|策略|做法|代价|
|---|---|---|
|**终止线程**|强制终止环路中的一个或多个线程|该线程的工作丢失，需重做|
|**资源抢占**|从某个线程强制剥夺资源转给其他线程|被抢占线程需回滚至安全状态|
|**超时放弃**|加锁时设置超时（`try_lock_for`），超时则放弃本次操作|实现简单，但可能影响业务逻辑|

> 死锁的**预防**优于**检测**，检测优于**恢复**。在设计阶段就应通过合理的锁策略和数据结构将死锁风险降至最低。

## 3.3 RAII 锁管理

代码示例：

```cpp
#include <print>
#include <thread>
#include <mutex>

static int shared_counter = 0;
static std::mutex mtx;  // 这是一把锁

void increaseWithLock(int times) {
  for (int i = 0; i < times; ++i) {
    // 使用 RAII 风格的锁管理
    std::lock_guard<std::mutex> guard(mtx);  // ⚠️ 临界区入口
    shared_counter++;
  }  // 循环结束，超出作用域，guard 变量析构，自动释放锁
}

int main() {
  std::thread t1(increaseWithLock, 100000);
  std::thread t2(increaseWithLock, 100000);
  t1.join();
  t2.join();
  std::println("Counter: {}", shared_counter);
}
```

不管执行多少次，输出结果始终是 200000：

```bash
Counter: 200000
```

> [!question] 为什么这里用 `lock_guard` 而不是手动 `mtx.lock()` 和 `mtx.unlock()`？

手动调用 `lock()`/`unlock()` 存在严重隐患：异常、提前 `return`、代码重构等情况都可能导致 `unlock()` 被跳过，锁就永远无法释放，程序会死锁（Deadlock）。C++ 推荐使用 **RAII（资源获取即初始化）** 风格的锁管理类，将锁的生命周期绑定到对象的作用域：

```cpp
{
    std::lock_guard<std::mutex> guard(mutex);  // 构造时加锁
    // —— 临界区 ——
    shared_counter++;
    // —— 临界区结束 ——
}   // guard 析构时自动解锁，无论是否发生异常
```

标准库提供了以下几种 RAII 锁管理类：

| 类型 | 特点 | 适用场景 |
|---|---|---|
| `std::lock_guard` | 构造加锁，析构解锁，不可手动控制 | 简单的临界区保护 |
| `std::unique_lock` | 支持延迟加锁、手动解锁、**条件变量配合** | 复杂控制流、条件等待 |
| `std::scoped_lock`（C++17） | 同时锁定多个互斥量，避免死锁 | 需要同时持有多个锁的场景 |

```cpp
// unique_lock 示例：与条件变量配合使用
std::unique_lock<std::mutex> lock(mutex);
cv.wait(lock, [] { return data_ready; });  // 等待期间自动释放锁
process(shared_data);
// 函数返回时自动解锁
```

> 参见 [4. 条件变量](#\ 4.\ 条件变量)。

## 3.4 锁的粒度控制

锁的粒度（Granularity）是指一次加锁所保护的数据范围，直接影响程序的并发性能：

**粒度过粗（Coarse-grained）**：用一把锁保护大量数据，临界区大，并发度低，线程长时间等待：

```cpp
std::mutex global_lock;

void thread_func() {
    std::lock_guard<std::mutex> guard(global_lock);
    step1();  // 这些操作未必都访问同一块共享数据
    step2();  // 却都被同一把锁串行化，并发性差
    step3();
}
```

**粒度过细（Fine-grained）**：为每个小数据单独加锁，并发度高，但锁的数量增多，管理复杂，且容易引发死锁：

```cpp
// 操作两个资源时分别加锁，若另一线程以相反顺序加锁，就会死锁
lockA.lock();
lockB.lock();  // ← 可能死锁
```

**实践原则**：临界区只包含**必须互斥的最小操作**，耗时的计算、I/O 等操作应移到临界区之外：

```cpp
// ❌ 不好：在锁内执行耗时操作
{
    std::lock_guard<std::mutex> guard(mutex);
    auto result = heavy_computation();  // 计算期间其他线程全部阻塞
    shared_data = result;
}

// ✅ 更好：锁外计算，锁内仅做赋值
auto result = heavy_computation();      // 计算在锁外进行
{
    std::lock_guard<std::mutex> guard(mutex);
    shared_data = result;               // 临界区只做必要的写操作
}
```

## 3.5 互斥锁的缺点

其实使用 `std::mutex` 是一种重量级的同步机制，**开销比较大**。原因如下：

- **内核参与**：当一个线程尝试获取锁但失败时，线程通常会被操作系统**挂起（Suspend）**。这涉及从“用户态”切换到“内核态”的巨大开销。当锁释放时，内核还要负责重新唤醒线程。这种**上下文切换**（Context Switch）涉及寄存器状态保存、缓存失效等，耗时通常在微秒（$\mu s$）级别。
- **昂贵的等待**：上下文切换需要保存当前 CPU 寄存器的状态、加载新线程的状态，这可能消耗数千个 CPU 周期。

# 4. 条件变量

`std::mutex`（互斥锁）只表达“锁是否可用”，但无法解决“**何时访问**”的问题。考虑一个经典的生产者-消费者场景：

> [!question] 消费者线程：队列为空时该怎么办？

- 方案一：**忙等（自旋）**

```cpp
void consumer() {
    std::unique_lock<std::mutex> lock(mtx);

    while (queue.empty()) {
        lock.unlock();
        lock.lock();    // 反复加解锁检查，白白消耗 CPU
    }
}
```

- 方案二：**定时轮询**

```cpp
void consumer() {
    std::unique_lock<std::mutex> lock(mtx);

    while (queue.empty()) {
        lock.unlock();
        std::this_thread::sleep_for(std::chrono::milliseconds(10));
        lock.lock();    // 有延迟，且仍有不必要的唤醒
    }
}
```

两种方案都有明显缺陷：忙等浪费 CPU，轮询引入延迟。我们真正需要的是：

```
队列为空 → 线程应该睡眠
队列非空 → 线程被唤醒去处理任务
```

这正是**条件变量**的职责。

条件变量是一种**线程间的通知机制**，允许线程在某个条件**不满足**时**原子性地挂起**，并在条件**成立**时被其他线程**唤醒**。严格意义上来说，条件变量的主要作用不是处理线程同步, 而是进行**线程的阻塞**。如果在多线程程序中只使用条件变量无法实现线程的同步, 因此它必须与互斥锁配合使用，二者分工明确：

```
std::mutex              → 保护共享数据，防止数据竞争
std::condition_variable → 协调线程执行时序，传递"条件已就绪"的信号
```

C++ 中提供了两种条件变量：

|类型|头文件|配套锁类型|特点|
|---|---|---|---|
|`std::condition_variable`|`<condition_variable>`|只能配合 `std::unique_lock<std::mutex>`|**性能更好**，推荐优先使用|
|`std::condition_variable_any`|`<condition_variable>`|可配合任意满足 BasicLockable 的锁|更通用，**开销略高**|

## 4.1 核心 API

### 4.1.1 等待方（消费者）

```cpp
// ① 无条件等待（不推荐，存在虚假唤醒风险）
void wait(std::unique_lock<std::mutex>& lock);

// ② 带谓词的等待（推荐）
template<class Predicate>
void wait(std::unique_lock<std::mutex>& lock, Predicate pred);
// 等价于：while (!pred()) { wait(lock); }

// ③ 带超时的等待（时间段）
template<class Rep, class Period>
std::cv_status wait_for(std::unique_lock<std::mutex>& lock,
                         const std::chrono::duration<Rep, Period>& rel_time);

// ④ 带超时且带谓词
template<class Rep, class Period, class Predicate>
bool wait_for(std::unique_lock<std::mutex>& lock,
              const std::chrono::duration<Rep, Period>& rel_time,
              Predicate pred);

// ⑤ 等待到绝对时间点
template<class Clock, class Duration>
std::cv_status wait_until(std::unique_lock<std::mutex>& lock,
                            const std::chrono::time_point<Clock, Duration>& abs_time);
```

第二种带谓词的 `wait` 内部实现等价于：

```cpp
template<class Predicate>
void wait(unique_lock<mutex>& lock, Predicate pred) {
    while (!pred()) {      // 循环检查，处理虚假唤醒
        wait(lock);        // 挂起等待
    }
    // pred() 返回 true 时才真正返回
}
```

> wait 中的把线程“挂起”其实是指**阻塞**该线程，即线程从“运行态 -> 阻塞态”。 

### 4.1.2 通知方（生产者）

```cpp
void notify_one();  // 唤醒一个等待线程（若有多个，随机选择）
void notify_all();  // 唤醒所有等待线程
```

> notify 中的把线程“唤醒”其实是指把线程**加入就绪队列**中，即线程从“阻塞态 -> 就绪态”。 

## 4.2 `wait()` 的原子语义

`wait()` 并非简单的“解锁 + 睡眠”，其内部执行是**原子的**，这一点至关重要：

```
调用 wait(lock) 时，原子地执行：
  1. 释放 lock 持有的互斥锁
  2. 将当前线程阻塞，加入等待队列 👉 CPU 不再执行这个线程：线程从运行态 -> 阻塞态
  ↑ 这两步是 wait 主动做的，是原子动作，中间不会有其他线程插入

被唤醒后：                            <- 唤醒是由 notify 完成：线程从阻塞态 -> 就绪态
  3. 重新竞争互斥锁                   <- 这步是由 操作系统调度+mutex 机制完成的
  4. 成功获取锁后，wait() 返回        <- 这是 wait 的返回条件
```

若释放锁和挂起线程不是原子的，就会出现**通知丢失（Lost Wakeup）** 问题：

```
// 若 wait 非原子：
消费者: unlock()          ← 刚解锁还未挂起
生产者:   lock()
生产者:   notify_one()    ← 通知发出，但消费者还没进入等待！
生产者:   unlock()
消费者:             wait() ← 进入等待，永远不会被唤醒
```

## 4.3 虚假唤醒（Spurious Wakeup）

**虚假唤醒（Spurious Wakeup）** ：指操作系统可能在没有 `notify` 的情况下唤醒线程，这是 POSIX 规范允许的底层行为。

先看一种错误做法：

```cpp
// ❌ 错误：不检查条件，虚假唤醒后直接操作数据
cv.wait(lock);
process(queue.front());  // 队列可能仍为空！

// ❌ 错误：使用 if
if (queue.empty()) {
    cv.wait(lock);
}
process(queue.front());
```

正确做法是在循环中检查条件：

```cpp
// ✅ 正确：手动循环检查
while (queue.empty()) {
    cv.wait(lock);
}

// ✅ 更优：使用带谓词的 wait，等价于上面的 while 循环
cv.wait(lock, [&] { return !queue.empty(); });  // 条件为 false，就阻塞；一旦条件为 true，就立即返回
```

> [!question]
> 那么为什么要用 `while` 循环检查，而不是 `if`？
> 因为存在 **虚假唤醒**，如果用 `if` 只判断一次，虚假唤醒后会**直接去取数据**，而此时**队列可能仍然是空**的，导致程序崩溃。带谓词的 `wait` 内部用 `while` 循环，自动处理了虚假唤醒。
> 
> 这里用具体例子说明，假设有一个消费者，用 `if` 来判断：
> 
> ```cpp
> // ❌ 错误写法
> void consumer() {
>     std::unique_lock<std::mutex> lock(mtx);
> 
>     if (queue.empty()) {        // 只检查一次
>         cv.wait(lock);          // 挂起...，如果这时候发生了“虚假唤醒”
>     }
>     // 醒来后直接到这里
>     int val = queue.front();    // 💥 这时候队列可能仍然是空的！
>     queue.pop();
> }
> ```
> 
> 换成 `while` 就安全了：
> 
> ```cpp
> // ✅ 正确写法
> void consumer() {
>     std::unique_lock<std::mutex> lock(mtx);
> 
>     while (q.empty()) {     // 每次醒来都重新检查
>         cv.wait(lock);      // 虚假唤醒后回到 while，再次判断
>     }
>     // 能走到这里，说明 q.empty() 为 false，队列一定有数据
>     int val = q.front();    // ✅ 安全
>     q.pop();
> }
> ```

如果我们把 wait 拆开来看，其实 `wait(lock, pred)` 内部等价于：

```cpp
while (queue.empty()) {   // 条件不满足就一直循环
    // 原子地执行以下两步：
    mtx.unlock();         //   1. 释放锁（让生产者能进入临界区）
    // 挂起，等待通知 ... //   2. 挂起线程（不占用 CPU），CPU 去执行其他任务
    mtx.lock();           // 被唤醒后：重新竞争锁，然后再检查队列是不是空的
}
// 循环退出 = 条件满足 = queue 不为空，可以安全取数据
```

由于是操作系统将线程移出了调度队列，即线程处于就绪队列中，所以哪怕这里用了 `while` 循环，也**不会造成 CPU 空转**。

> [!success]
> `while` 的本质就是：**不管线程因为什么原因醒来，都必须重新验证条件是否真的满足，不满足就继续阻塞着**。

## 4.4 `notify_one` vs `notify_all`

```cpp
cv.notify_one();   // 唤醒等待（阻塞）队列中的一个线程
cv.notify_all();   // 唤醒所有等待线程
```

**何时用 `notify_one`**：所有等待线程的逻辑相同，唤醒一个就足以处理当前变化，且唤醒多个会造成不必要的竞争（惊群效应）：

```cpp
// 生产者每次生产一个任务，只需唤醒一个消费者
queue.push(task);
cv.notify_one();   // ✅ 高效，避免多个消费者无谓竞争
```

**何时用 `notify_all`**：

```cpp
// 场景一：等待线程的条件各不相同，需要每个线程自行检查
cv.notify_all();   // 广播，让每个线程检查自己的谓词

// 场景二：状态发生了根本性变化（如程序关闭），需通知所有线程
stop_ = true;
cv.notify_all();   // 唤醒所有工作线程，使其检测到停止标志

// 场景三：一次性产生了大量数据
// 批量入队后唤醒所有消费者并行处理
cv.notify_all();
```

## 4.5 超时等待

在等待时间上限敏感的场景（如网络请求、实时系统），应使用带超时的变体：

```cpp
std::mutex mtx;
std::condition_variable cv;
bool data_ready = false;

void consumer() {
    std::unique_lock<std::mutex> lock(mtx);

    // wait_for：等待一段时间
    auto status = cv.wait_for(lock,
                               std::chrono::seconds(5),
                               [&] { return data_ready; });
    if (status) {
        // 条件满足，正常处理
        process_data();
    } else {
        // 超时，执行降级逻辑
        handle_timeout();
    }
}

void consumer_until() {
    std::unique_lock<std::mutex> lock(mtx);

    // wait_until：等到某个绝对时间点
    auto deadline = std::chrono::steady_clock::now() + std::chrono::seconds(5);
    bool ok = cv.wait_until(lock, deadline, [&] { return data_ready; });
    
    // 推荐使用 steady_clock（单调递增，不受系统时间调整影响）
    // 避免使用 system_clock（可能因 NTP 等原因跳变）
}
```

`wait_for`/`wait_until` 带谓词版本返回 `bool`：

- `true`：谓词为真，条件满足后返回
- `false`：超时返回，谓词仍为假

## 4.6 经典模式

### 4.6.1 生产者-消费者

这是一个简单的生产者-消费者模型：

```cpp
#include <print>
#include <string>
#include <thread>
#include <queue>
#include <mutex>
#include <condition_variable>

std::queue<int> q;           // 缓冲区：生产者写入，消费者读取
std::mutex mtx;              // 互斥锁：保护 q 的并发访问
std::condition_variable cv;  // 条件变量：协调两个线程的执行时序

void producer(const std::string &name) {
  for (int i = 1; i <= 5; ++i) {
    {
      std::lock_guard<std::mutex> lock(mtx);  // ① 加锁
      q.push(i);                              // ② 写入数据
      std::println("Producer {} produced: {}", name, i);
    }  // ③ lock_guard 析构，自动解锁

    cv.notify_one();  // ④ 解锁之后再通知消费者

    std::this_thread::sleep_for(  // ⑤ 模拟生产耗时
        std::chrono::milliseconds(500));
  }
}

void consumer(const std::string &name) {
  while (true) {
    std::unique_lock<std::mutex> lock(mtx);  // ① 加锁

    cv.wait(lock, [] { return !q.empty(); });  // ② 核心：等待条件

    int val = q.front();  // ③ 取出数据
    q.pop();

    std::println("Consumer {} consumed: {}", name, val);

    if (val == 5)
      break;  // ④ 取到 5 就退出
  }
  // ⑤ unique_lock 析构，自动解锁
}

int main() {
  std::thread producer_thread1(producer, "Producer 1");  // 生产者 1
  std::thread consumer_thread1(consumer, "Consumer 1");  // 消费者 1

  producer_thread1.join();
  consumer_thread1.join();
}
```

**一个重要的性能细节**：`notify_one()` 应在**锁释放之后**调用：

```cpp
// ❌ 持锁通知：消费者被唤醒后立刻阻塞在锁上，多一次无谓的上下文切换
{
    std::unique_lock<std::mutex> lock(mutex_);
    queue_.push(value);
    cv_.notify_one();    // 锁还没释放，这时候把消费者唤醒，消费者又得等锁
}

// ✅ 解锁后通知：消费者唤醒时锁已经可用，减少一次竞争
{
    std::unique_lock<std::mutex> lock(mutex_);
    queue_.push(value);
}                        // 先释放锁
cv_.notify_one();        // 再通知，消费者可以直接获取锁
```

### 4.6.2 一次性事件（栅栏）

多个线程等待某个事件发生，事件发生后所有线程继续执行：

```cpp
class Latch {
public:
    explicit Latch(int count) : count_(count) {}

    // 计数减一，减到 0 时唤醒所有等待者
    void count_down() {
        std::unique_lock<std::mutex> lock(mutex_);
        if (--count_ == 0) {
            cv_.notify_all();
        }
    }

    // 等待计数归零
    void wait() {
        std::unique_lock<std::mutex> lock(mutex_);
        cv_.wait(lock, [this] { return count_ == 0; });
    }

private:
    std::mutex mutex_;
    std::condition_variable cv_;
    int count_;
};

// 用法：主线程等待所有子线程完成初始化
Latch ready_latch(3);

void worker(int id) {
    initialize(id);
    ready_latch.count_down();   // 通知主线程"我准备好了"
    do_work(id);
}

int main() {
    std::thread t1(worker, 1);
    std::thread t2(worker, 2);
    std::thread t3(worker, 3);
    
    ready_latch.wait();          // 等待三个线程全部初始化完成
    std::cout << "所有线程就绪，开始处理\n";
    
    t1.join(); t2.join(); t3.join();
}
```

> C++20 已将此模式标准化为 `std::latch` 和 `std::barrier`，新代码可直接使用。

## 4.7 常见错误

**错误一：在锁外调用 `wait()`**

```cpp
// ❌ wait() 必须在持有锁的情况下调用
cv.wait(lock);   // lock 必须处于 locked 状态，否则未定义行为
```

**错误二：不检查谓词，忽视虚假唤醒**

```cpp
// ❌ 未使用谓词，虚假唤醒后直接操作数据
cv.wait(lock);
process(queue.front());  // 可能崩溃
```

**错误三：用 `notify` 替代数据修改**

```cpp
// ❌ 错误：没有修改共享状态就发送通知，消费者醒来条件仍不成立
cv.notify_one();          // 没有先修改 data_ready

// ✅ 正确：先改变状态，再通知
data_ready = true;
cv.notify_one();
```

**错误四：用 `condition_variable` 配合非 `unique_lock`**

```cpp
std::lock_guard<std::mutex> guard(mtx);
cv.wait(guard, pred);     // ❌ 编译错误：lock_guard 不支持手动解锁
                          //    条件变量需要能在等待时释放锁

std::unique_lock<std::mutex> lock(mtx);
cv.wait(lock, pred);      // ✅ unique_lock 支持手动控制
```

# 5. 读写锁

`std::mutex` 实施的是**无差别的互斥**——无论线程是读操作还是写操作，都必须独占资源。但在实际工程中，对共享数据的访问往往呈现出**读多写少**的特征（如配置表、缓存、路由表等）。

用普通互斥锁保护这类数据存在明显的性能浪费：

```
线程A（读）  ████░░░░░░░░░░░░░░░
线程B（读）  ░░░░████░░░░░░░░░░░   ← 读操作本不会修改数据，
线程C（读）  ░░░░░░░░████░░░░░░░     却被强制串行，并发度极低
线程D（写）  ░░░░░░░░░░░░████░░░
```

读写锁（Read-Write Lock）针对这一场景做了专门优化，其核心语义是：

> **读者之间不互斥，写者与任何人互斥。**

```
线程A（读）  ████████████░░░░░░░
线程B（读）  ████████████░░░░░░░   ← 多个读者可同时持有锁
线程C（读）  ████████████░░░░░░░
线程D（写）  ░░░░░░░░░░░░████░░░   ← 写者独占，等待所有读者退出
```

## 5.1 使用方式

C++17 引入了 `std::shared_mutex`（头文件 `<shared_mutex>`），提供两种加锁模式：

|模式|语义|适用操作|
|---|---|---|
|**独占锁（Exclusive Lock）**|同一时刻只有一个线程可持有|写操作|
|**共享锁（Shared Lock）**|同一时刻多个线程可同时持有|读操作|

两种模式的兼容性：

||独占锁（写）|共享锁（读）|
|---|---|---|
|**独占锁（写）**|❌ 互斥|❌ 互斥|
|**共享锁（读）**|❌ 互斥|✅ 兼容|

`std::shared_mutex` 的成员函数：

```cpp
// 独占模式（写）
void lock();              // 独占加锁，阻塞直到获取
bool try_lock();          // 尝试独占加锁，失败立即返回 false
void unlock();            // 释放独占锁

// 共享模式（读）
void lock_shared();       // 共享加锁，阻塞直到获取
bool try_lock_shared();   // 尝试共享加锁，失败立即返回 false
void unlock_shared();     // 释放共享锁
```

与 `std::mutex` 搭配 `std::lock_guard` 类似，`std::shared_mutex` 有专属的 RAII 管理类：

|RAII 类|对应锁模式|说明|
|---|---|---|
|`std::shared_lock`|共享锁（读）|构造时 `lock_shared()`，析构时 `unlock_shared()`|
|`std::unique_lock`|独占锁（写）|构造时 `lock()`，析构时 `unlock()`|
|`std::lock_guard`|独占锁（写）|更轻量，不支持手动控制|

代码示例：

```cpp
#include <shared_mutex>
#include <thread>
#include <iostream>
#include <vector>

class SafeConfig {
public:
    // 读操作：使用共享锁，多个线程可同时读取
    std::string get(const std::string& key) const {
        std::shared_lock<std::shared_mutex> lock(rw_mutex_);  // 共享加锁
        auto it = data_.find(key);
        return it != data_.end() ? it->second : "";
    }   // 析构时自动 unlock_shared()

    // 写操作：使用独占锁，同一时刻只有一个线程可写
    void set(const std::string& key, const std::string& value) {
        std::unique_lock<std::shared_mutex> lock(rw_mutex_);  // 独占加锁
        data_[key] = value;
    }   // 析构时自动 unlock()

private:
    mutable std::shared_mutex rw_mutex_;  // mutable 允许在 const 函数中加锁
    std::map<std::string, std::string> data_;
};
```

## 5.2 锁升级与锁降级

这是读写锁使用中最容易踩坑的地方，C++ 标准对此有明确限制。

### 5.2.1 锁升级（Shared → Exclusive）：不支持

"先获取共享锁读取数据，发现需要修改，再升级为独占锁"——这种直觉上合理的操作在 `std::shared_mutex` 中**不被支持**，强行操作会导致死锁：

```cpp
// ❌ 错误示范：企图在持有共享锁的情况下升级为独占锁
void dangerous_upgrade(std::shared_mutex& mtx) {
    std::shared_lock<std::shared_mutex> r_lock(mtx);  // 获取共享锁
    auto val = read_data();

    if (need_modify(val)) {
        r_lock.unlock();         // 必须先手动释放共享锁
        // ⚠️ 此处存在窗口期：锁已释放但独占锁未获取，数据可能被其他线程修改
        std::unique_lock<std::shared_mutex> w_lock(mtx);  // 再获取独占锁
        modify_data(val);
    }
}
```

释放共享锁到获取独占锁之间存在一个**窗口期**，其他线程可能趁机修改数据，导致读取到的值已经过期。如果业务要求原子性的读-改-写，应当**从一开始就直接获取独占锁**：

```cpp
// ✅ 需要读后修改时，直接使用独占锁
void correct_read_modify(std::shared_mutex& mtx) {
    std::unique_lock<std::shared_mutex> w_lock(mtx);
    auto val = read_data();       // 在独占锁保护下读取
    if (need_modify(val)) {
        modify_data(val);         // 在同一把锁下修改，无窗口期
    }
}
```

### 5.2.2 锁降级（Exclusive → Shared）：需手动实现

标准库同样不提供原子降级操作，但降级的风险远低于升级，可通过手动顺序操作实现：

```cpp
void manual_downgrade(std::shared_mutex& mtx) {
    std::unique_lock<std::shared_mutex> w_lock(mtx);
    modify_data();               // 写操作完成

    // 手动降级：先获取共享锁，再释放独占锁
    mtx.lock_shared();
    w_lock.unlock();             // 释放独占锁，此后其他读者可进入

    read_data();                 // 以共享锁进行后续读操作
    mtx.unlock_shared();
}
```

## 5.3 带超时的读写锁

C++14 引入了 `std::shared_timed_mutex`，在 `std::shared_mutex` 的基础上增加了超时版本的加锁接口，适用于需要**避免无限期阻塞**的场景：

```cpp
#include <shared_mutex>

std::shared_timed_mutex timed_mtx;

// 带超时的独占加锁（写）
bool write_with_timeout() {
    auto deadline = std::chrono::steady_clock::now() + std::chrono::milliseconds(100);
    
    if (timed_mtx.try_lock_until(deadline)) {
        // 成功获取独占锁
        modify_data();
        timed_mtx.unlock();
        return true;
    }
    // 超时未获取到锁
    return false;
}

// 带超时的共享加锁（读）
bool read_with_timeout() {
    if (timed_mtx.try_lock_shared_for(std::chrono::milliseconds(50))) {
        // 成功获取共享锁
        auto val = read_data();
        timed_mtx.unlock_shared();
        return true;
    }
    return false;
}
```

两者的接口对比：

|接口|`shared_mutex`|`shared_timed_mutex`|
|---|---|---|
|引入版本|C++17|C++14|
|超时加锁|❌|✅ `try_lock_for` / `try_lock_until`|
|超时共享加锁|❌|✅ `try_lock_shared_for` / `try_lock_shared_until`|
|性能|略高|略低（需维护超时状态）|

## 5.4 读写锁的缺点

1. **写者饥饿（Writer Starvation）**

若读操作持续不断，写者可能长期无法获取独占锁，陷入饥饿：

```
线程R1（读）  ████████████████████████████████···
线程R2（读）      ████████████████████████████···
线程R3（读）          ████████████████████████···
线程W （写）  ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░···  ← 永远在等待
```

C++ 标准未规定 `std::shared_mutex` 的公平性策略，不同平台实现可能不同。在写操作优先级较高的场景下，需要额外的设计（如限制同时持有共享锁的读者数量，或使用带优先级的自定义锁）。

2. **读写锁并非总是优于互斥锁**

读写锁的内部实现比 `std::mutex` 更复杂，维护读者计数、处理写者等待等都有额外开销。在以下情况下，读写锁可能**劣于**普通互斥锁：

```cpp
// 读写比接近 1:1 时，读写锁的额外管理开销可能得不偿失
// 临界区极短时（如单个整数赋值），std::atomic 是更好的选择
// 高竞争场景下，两种锁的性能差异会趋于收敛
```

经验规律：**读操作占比超过 80%，且临界区不是极短的原子操作时，读写锁才有明显收益**。最终应以实际性能测试为准。

3. **缓存一致性开销（False Sharing）**

读写锁内部需要维护读者计数器，多个读者并发访问时会频繁修改这个计数器，若它与被保护数据处于同一缓存行，反而会造成缓存行频繁失效：

```cpp
// 确保锁对象与数据不在同一缓存行
struct alignas(64) PaddedMutex {   // 64 字节对齐，独占一条缓存行
    std::shared_mutex mtx;
};
```

## 5.5 实战：线程安全的读写缓存

```cpp
#include <functional>
#include <shared_mutex>
#include <string>
#include <unordered_map>
#include <optional>
#include <thread>
#include <iostream>

template <typename K, typename V>
class RWCache {
 public:
  // 读：共享锁，支持多线程并发读取
  std::optional<V> get(const K &key) const {
    std::shared_lock<std::shared_mutex> lock(mutex_);
    auto it = cache_.find(key);
    if (it == cache_.end())
      return std::nullopt;
    return it->second;
  }

  // 写：独占锁，串行写入
  void put(const K &key, V value) {
    std::unique_lock<std::shared_mutex> lock(mutex_);
    cache_[key] = std::move(value);
  }

  // 读-改-写：全程独占锁，保证原子性
  V get_or_create(const K &key, std::function<V()> factory) {
    // 先尝试共享锁快速读取
    {
      std::shared_lock<std::shared_mutex> lock(mutex_);
      auto it = cache_.find(key);
      if (it != cache_.end())
        return it->second;
    }
    // 未命中，升级为独占锁，再次检查（防止窗口期内其他线程已插入）
    std::unique_lock<std::shared_mutex> lock(mutex_);
    auto it = cache_.find(key);
    if (it != cache_.end())
      return it->second;  // 双重检查

    auto val = factory();
    cache_[key] = val;
    return val;
  }

  size_t size() const {
    std::shared_lock<std::shared_mutex> lock(mutex_);
    return cache_.size();
  }

 private:
  mutable std::shared_mutex mutex_;
  std::unordered_map<K, V> cache_;
};

int main() {
  RWCache<std::string, int> cache;

  // 多个读线程并发读取
  std::vector<std::thread> readers;
  for (int i = 0; i < 5; ++i) {
    readers.emplace_back([&cache, i] {
      auto val = cache.get("key");
      std::cout << "Reader " << i << ": " << (val ? std::to_string(*val) : "miss") << "\n";
    });
  }

  // 写线程
  std::thread writer([&cache] {
    cache.put("key", 42);
    std::cout << "Writer: wrote 42\n";
  });

  for (auto &r : readers)
    r.join();
  writer.join();
}
```

# 6. 原子变量

C++11 提供了 `<atomic>`。可以利用 CPU 指令保证原子性，速度比 `std::mutex` 快得多，且不会死锁。

```cpp
#include <atomic>

std::atomic<int> count_a(0); // 原子整型

void increaseWithAtomic(int times) {
  for (int i = 0; i < times; ++i) {
    counter_a++;  // 这一行直接编译为原子硬件指令
  }
}
```

原子操作完全在**用户态**完成，原子操作**不需要陷入内核**，它是由 **CPU 硬件**直接保证的，而不是由操作系统保证的。由于它不需要操作系统的介入，线程永远不会被挂起。它通过 CPU 的指令集直接在硬件层面保证操作的不可分割性。其耗时通常在纳秒（$ns$）级别。

虽然 `std::atomic` 极快，但它并不是万能的：

| 特性 | `std::atomic` | `std::mutex` |
| :--- | :--- | :--- |
| **工作层级** | 硬件指令层 | 操作系统原语（futex / 内核对象）|
| **受保护的数据** | 仅限单个**简单**变量（int, bool, 指针） | 可以保护**复杂**的逻辑块、容器、多变量关联 |
| **逻辑复杂度** | 仅限于加减、交换等简单操作 | 适合任何复杂的业务逻辑 |
| **等待策略** | 忙轮询（自旋），消耗 CPU | 挂起线程，不占 CPU，但唤醒慢 |

**结论**：如果你只是想保护一个**计数器**或一个**标志位**，用 `std::atomic`。如果你要保护一个 `std::vector` 的插入逻辑或者**一段复杂的代码**，请务必使用 `std::mutex`。

> [!warning]
> 别混淆这两个概念：
> 
> | 概念 | 含义 | 例子 |
> |---|---|---|
> | **特权指令** | 只能在内核态执行，用户态执行会触发异常 | `HLT`, `LGDT`, `IN/OUT` |
> | **原子指令** | 执行结果不可被打断，但用户态可以直接用 | `LOCK ADD`, `CMPXCHG`, `XCHG` |

# 7. 信号量

互斥锁解决的是"同一时刻只有一个线程访问"的问题，条件变量解决的是"条件满足时才继续执行"的问题，但二者都无法直接表达一类常见需求：

> **控制同时访问某资源的线程数量上限。**

典型场景：数据库连接池限制最多 10 个并发连接，线程池限制并发任务数，限流器控制 QPS……这类“**有限资源的并发访问控制**”正是信号量的核心职责。

信号量（Semaphore）是由 E.W. Dijkstra 于 1965 年提出的同步原语，其本质是一个**带有原子操作的非负整数计数器**，支持两种操作：

```
P 操作（acquire / wait / down）：
    计数器 > 0 → 计数器减 1，线程继续执行
    计数器 = 0 → 线程阻塞，直到计数器 > 0

V 操作（release / signal / up）：
    计数器加 1
    若有线程在等待 → 唤醒其中一个
```

计数器的初始值代表**可用资源的数量**，P 操作表示"申请一个资源"，V 操作表示"归还一个资源"。

C++20 之前，标准库没有提供信号量，开发者只能用 `mutex` + `condition_variable` 手动模拟。C++20 在 `<semaphore>` 头文件中引入了两个类：

|类型|语义|典型用途|
|---|---|---|
|`std::counting_semaphore<N>`|计数范围 [0, N]，N 为编译期上限|资源池、限流、并发控制|
|`std::binary_semaphore`|计数只有 0 和 1|互斥、一次性事件通知|

其中 `std::binary_semaphore` 实际上是 `std::counting_semaphore<1>` 的别名：

```cpp
using binary_semaphore = std::counting_semaphore<1>;
```

## 7.1 核心 API

```cpp
// 构造：指定初始计数值，必须在 [0, LeastMaxValue] 范围内
explicit counting_semaphore(std::ptrdiff_t desired);

// P 操作：申请资源
void acquire();                    // 阻塞直到计数器 > 0，然后减 1
bool try_acquire();                // 非阻塞，成功返回 true，失败返回 false
bool try_acquire_for(duration);    // 超时等待（时间段）
bool try_acquire_until(time_point);// 超时等待（绝对时间点）

// V 操作：归还资源
void release(std::ptrdiff_t update = 1);  // 计数器加 update，唤醒等待线程
```

**模板参数 `LeastMaxValue`** 是计数器的编译期上限，标准库可以据此进行内部优化（如 `binary_semaphore` 可以用单个原子位实现，比通用计数信号量更轻量）。`LeastMaxValue` 的实际最大值可通过静态成员 `max()` 查询：

```cpp
auto max_val = std::counting_semaphore<10>::max();
```

## 7.2 信号量 vs 互斥锁

信号量与互斥锁有本质区别，混淆二者是常见的错误来源：

|特性|`std::mutex`|`std::counting_semaphore`|
|---|---|---|
|计数范围|0 或 1|0 到 N|
|所有权|有（加锁线程必须解锁）|无（任何线程可 release）|
|用途|互斥访问临界区|资源计数、线程间通知|
|递归性|不可递归（`shared_mutex`）|无所有权概念，无此限制|
|跨线程操作|不安全（未定义行为）|合法且常见|

**所有权差异**是最重要的区别：

```cpp
std::mutex mtx;
mtx.lock();             // 线程 A 加锁
// 线程 B 调用 mtx.unlock() → 未定义行为！锁必须由持有者释放

std::binary_semaphore sem(0);
// 线程 A 调用 sem.acquire() → 阻塞
sem.release();          // 线程 B 调用 release → 完全合法，这正是通知模式的基础
```

## 7.3 经典模式

### 7.3.1 资源池限流

控制同时使用某资源的线程数上限：

```cpp
#include <semaphore>
#include <thread>
#include <iostream>
#include <vector>

// 数据库连接池：最多允许 3 个并发连接
class ConnectionPool {
public:
    explicit ConnectionPool(int max_conn)
        : sem_(max_conn), max_conn_(max_conn) {}

    // 获取连接（RAII 封装）
    class Connection {
    public:
        Connection(ConnectionPool& pool, int id)
            : pool_(pool), id_(id) {
            std::cout << "线程 " << std::this_thread::get_id()
                      << " 获取连接 #" << id_ << "\n";
        }
        ~Connection() {
            pool_.sem_.release();   // 归还连接，唤醒等待线程
            std::cout << "线程 " << std::this_thread::get_id()
                      << " 释放连接 #" << id_ << "\n";
        }
        // 禁止拷贝，防止重复释放
        Connection(const Connection&) = delete;
        Connection& operator=(const Connection&) = delete;

    private:
        ConnectionPool& pool_;
        int id_;
    };

    Connection acquire() {
        sem_.acquire();   // 申请一个连接槽位，无槽位时阻塞
        return Connection(*this, ++conn_id_);
    }

    // 带超时的获取
    std::optional<Connection> try_acquire_for(std::chrono::milliseconds timeout) {
        if (sem_.try_acquire_for(timeout)) {
            return Connection(*this, ++conn_id_);
        }
        return std::nullopt;  // 超时，无可用连接
    }

private:
    std::counting_semaphore<> sem_;
    std::atomic<int> conn_id_{0};
    int max_conn_;
};

int main() {
    ConnectionPool pool(3);  // 最多 3 个并发连接

    std::vector<std::thread> threads;
    for (int i = 0; i < 8; ++i) {
        threads.emplace_back([&pool, i] {
            auto conn = pool.acquire();   // 超过 3 个时自动阻塞等待
            // 模拟数据库操作
            std::this_thread::sleep_for(std::chrono::milliseconds(100));
        });
    }
    for (auto& t : threads) t.join();
}
```

### 7.3.2 线程间单向通知

`binary_semaphore` 初始值为 0，天然适合表达"等待某件事发生"：

```cpp
#include <semaphore>

std::binary_semaphore data_ready(0);  // 初始为 0，表示数据未就绪
std::string shared_data;

void producer() {
    shared_data = "Hello from producer";
    // 数据写完后发出信号
    data_ready.release();              // 计数 0 → 1，唤醒消费者
}

void consumer() {
    data_ready.acquire();              // 计数为 0 时阻塞，等待 producer
    std::cout << shared_data << "\n";  // 安全：producer 已写完数据
}

int main() {
    std::thread t1(producer);
    std::thread t2(consumer);
    t1.join();
    t2.join();
}
```

与条件变量相比，这里无需互斥锁即可实现安全的线程通知，代码更简洁。

### 7.3.3 生产者-消费者（有界缓冲区）

用两个信号量分别追踪"空槽位数量"和"已填充数量"，这是信号量最经典的应用之一：

```cpp
#include <semaphore>
#include <mutex>
#include <queue>

template<typename T>
class BoundedQueue {
public:
    explicit BoundedQueue(size_t capacity)
        : empty_slots_(capacity)   // 初始全为空槽
        , filled_slots_(0)         // 初始无数据
        , capacity_(capacity) {}

    // 生产者：写入数据
    void push(T value) {
        empty_slots_.acquire();     // 等待空槽位（满时阻塞）
        {
            std::lock_guard<std::mutex> lock(mutex_);
            buffer_.push(std::move(value));
        }
        filled_slots_.release();    // 通知消费者有新数据
    }

    // 消费者：读取数据
    T pop() {
        filled_slots_.acquire();    // 等待有数据（空时阻塞）
        T value;
        {
            std::lock_guard<std::mutex> lock(mutex_);
            value = std::move(buffer_.front());
            buffer_.pop();
        }
        empty_slots_.release();     // 通知生产者有空槽位
        return value;
    }

    // 带超时的消费
    std::optional<T> pop_for(std::chrono::milliseconds timeout) {
        if (!filled_slots_.try_acquire_for(timeout))
            return std::nullopt;    // 超时无数据

        T value;
        {
            std::lock_guard<std::mutex> lock(mutex_);
            value = std::move(buffer_.front());
            buffer_.pop();
        }
        empty_slots_.release();
        return value;
    }

private:
    std::counting_semaphore<> empty_slots_;   // 剩余空槽数
    std::counting_semaphore<> filled_slots_;  // 已填充数据数
    std::mutex mutex_;                         // 保护 buffer_ 的并发访问
    std::queue<T> buffer_;
    size_t capacity_;
};
```

两个信号量的状态始终满足不变式：`empty_slots + filled_slots == capacity`，这由 acquire/release 的配对调用自动保证，无需额外检查。

### 7.3.4 多线程任务编排

用信号量实现任务间的依赖关系，确保执行顺序：

```cpp
// 任务依赖关系：
//   task_A ──┬──► task_C ──► task_D
//   task_B ──┘

std::binary_semaphore a_done(0);
std::binary_semaphore b_done(0);
std::binary_semaphore c_done(0);

void task_A() {
    std::cout << "A 执行\n";
    a_done.release();
}

void task_B() {
    std::cout << "B 执行\n";
    b_done.release();
}

void task_C() {
    a_done.acquire();   // 等待 A 完成
    b_done.acquire();   // 等待 B 完成
    std::cout << "C 执行（A 和 B 均已完成）\n";
    c_done.release();
}

void task_D() {
    c_done.acquire();   // 等待 C 完成
    std::cout << "D 执行\n";
}

int main() {
    std::thread tA(task_A);
    std::thread tB(task_B);
    std::thread tC(task_C);
    std::thread tD(task_D);

    tA.join(); tB.join(); tC.join(); tD.join();
    // 无论线程调度顺序如何，输出顺序始终满足依赖约束
}
```

## 7.4 补充

在不能使用 C++20 的项目中，可以用 `mutex` + `condition_variable` 这种方式模拟信号量：

```cpp
class Semaphore {
public:
    explicit Semaphore(int count = 0) : count_(count) {}

    void release(int update = 1) {
        {
            std::unique_lock<std::mutex> lock(mutex_);
            count_ += update;
        }
        // 根据 update 决定唤醒策略
        if (update == 1)
            cv_.notify_one();
        else
            cv_.notify_all();
    }

    void acquire() {
        std::unique_lock<std::mutex> lock(mutex_);
        cv_.wait(lock, [this] { return count_ > 0; }); // 处理虚假唤醒
        --count_;
    }

    bool try_acquire_for(std::chrono::milliseconds timeout) {
        std::unique_lock<std::mutex> lock(mutex_);
        bool ok = cv_.wait_for(lock, timeout, [this] { return count_ > 0; });
        if (ok) --count_;
        return ok;
    }

private:
    std::mutex mutex_;
    std::condition_variable cv_;
    int count_;
};
```

标准库的 `std::counting_semaphore` 在实现上通常比这个模拟版本更高效，底层可直接使用 futex 或平台原子指令，**有条件应优先使用标准库版本**。

## 7.5 常见陷阱

**陷阱一：release 次数超过 acquire，导致计数溢出**

```cpp
std::counting_semaphore<3> sem(3);
sem.acquire();   // 计数: 2
sem.release();   // 计数: 3
sem.release();   // ❌ 计数: 4，超过最大值，未定义行为
```

`release` 的参数 `update` 使计数超过构造时指定的 `LeastMaxValue` 是未定义行为，必须确保 release 与 acquire 严格配对。

**陷阱二：用信号量模拟互斥锁，却在同一线程 acquire 两次**

```cpp
std::binary_semaphore sem(1);
sem.acquire();   // 模拟 lock
sem.acquire();   // ❌ 自己阻塞自己：信号量无所有权概念，不会检测死锁
```

信号量没有所有权，运行时不会检测"同一线程重复申请"，直接死锁。互斥需求请用 `std::mutex`。

**陷阱三：异常导致 release 未执行，资源泄漏**

```cpp
sem.acquire();
risky_operation();  // 若抛出异常……
sem.release();      // ❌ 永远不会执行，计数永久减少
```

应通过 RAII 封装确保异常安全：

```cpp
class SemaphoreGuard {
public:
    explicit SemaphoreGuard(std::counting_semaphore<>& sem) : sem_(sem) {
        sem_.acquire();
    }
    ~SemaphoreGuard() { sem_.release(); }
    SemaphoreGuard(const SemaphoreGuard&) = delete;
private:
    std::counting_semaphore<>& sem_;
};

// 使用
SemaphoreGuard guard(sem);  // 构造时 acquire，析构时自动 release
risky_operation();           // 异常也能正确释放
```

# 9. 各函数对线程状态的影响

各函数对线程状态的影响

1. **`cv.wait()` → 运行态变阻塞态**

```cpp
cv.wait(lock);
```

```
运行态
  │
  ├─ 原子释放锁
  ├─ 将自己从调度队列移除
  └─ 进入阻塞态，等待 notify 信号
          │
          │ notify_one() / notify_all() 到来
          ▼
       就绪态（重新竞争锁和 CPU）
```

2. **`std::this_thread::yield()` → 运行态变就绪态**

```cpp
std::this_thread::yield();
```

```
运行态
  │
  └─ 主动放弃当前时间片
     但线程仍具备运行条件
          │
          ▼
       就绪态（重新加入调度队列末尾，等待下次调度）
```

`yield` 只是礼让 CPU，线程随时可以被重新调度，常用于自旋等待中减少 CPU 空转：

```cpp
// 自旋锁中用 yield 避免完全空转
while (!flag.load()) {
    std::this_thread::yield();  // 让出 CPU，但随时准备再次运行
}
```

3. **`std::this_thread::sleep_for()` → 运行态变阻塞态**

```cpp
std::this_thread::sleep_for(std::chrono::milliseconds(100));
```

```
运行态
  │
  └─ 进入阻塞态，等待计时器到期
          │
          │ 100ms 后，计时器触发
          ▼
       就绪态（等待 CPU 调度）
```

与 `wait` 的区别在于唤醒条件不同：`sleep` 等待时间，`wait` 等待通知信号。

4. **`mutex.lock()` 失败 → 运行态变阻塞态**

```cpp
std::unique_lock<std::mutex> lock(mtx);  // 锁被其他线程占用时
```

```
运行态
  │
  ├─ 尝试获取锁
  └─ 锁已被占用，进入阻塞态，等待锁释放
          │
          │ 锁被释放，操作系统唤醒等待线程之一
          ▼
       就绪态
```

5. **`t.join()` → 调用线程变阻塞态**

```cpp
t.join();  // 在主线程中调用
```

```
主线程（运行态）
  │
  └─ 进入阻塞态，等待 t 线程执行完毕
          │
          │ t 线程的函数返回，线程终止
          ▼
       主线程回到就绪态
```

6. **`std::this_thread::yield()` vs `sleep_for()` vs `wait()` 对比**

|特性|`yield()`|`sleep_for()`|`wait()`|
|---|---|---|---|
|执行后状态|就绪态 (Ready)|阻塞态 (Blocked)|阻塞态 (Blocked)|
|唤醒条件|调度器再次选中|计时器到期|收到 `notify` 信号|
|CPU 占用|低（依然参与调度）|无|无|
|响应延迟|极低|固定（受系统精度影响）|取决于通知时机|
|典型场景|自旋锁减负、防止死循环卡死|定时任务、模拟耗时|生产者-消费者、事件同步|

7. **总结**

```
cv.wait()        → 阻塞态，等待 notify 唤醒
mutex.lock()     → 阻塞态（锁冲突时），等待锁释放
sleep_for/until  → 阻塞态，等待时间到期
join()           → 调用者进阻塞态，等待目标线程结束
yield()          → 就绪态，主动让出 CPU 但随时可重新运行
thread 构造完成  → 就绪态，等待调度器分配 CPU
线程函数返回     → 终止态，资源待回收
```
