# 1. 设置 Non-blocking

在严谨的 I/O 多路复用编程中，通过 `socket(...)` 获得的 `listen_fd` 和通过 `accept(...)` 获得的 `conn_fd` **都建议设置为非阻塞模式**（epoll ET 模式下是**必须**），但它们应对的风险场景完全不同。

## 1.1 设置 `listen_fd` 为非阻塞模式

虽然负责监听的线程告诉你 `listen_fd` 可读（有新连接），但你依然面临 **“惊群效应”** 或 **“连接被客户端撤回”** 的风险。

> [!example] 场景模拟：消失的新连接 (The Disappearing Connection)
> 假设你正在使用 `epoll` 或 `select` 监控 `listen_fd`。
> 1. **事件发生**：一个客户端向服务器发起连接请求，完成了 TCP 三次握手。内核把这个连接放入“全连接队列”。
> 2. **通知就绪**：`epoll_wait` 告诉你：`listen_fd` 管理的全连接队列中有新连接来了！
> 3. **意外发生**：就在你准备调用 `accept` 之前的 **0.0001 秒**，这个客户端突然由于断电或进程崩溃，内核自动给服务器发了一个 `RST` 报文，撤回了连接。
> 4. **内核处理**：内核收到 `RST`，把刚才那个连接从队列里删除了。此时，**全连接队列变空了**。

结果对比：
- **如果 `listen_fd` 设置为阻塞模式**：你调用 `accept`。由于队列空了，`accept` 会“**死等**”下一个客户端进程的到来。此时如果有另外 1000 个已经连上的老客户在发消息，你的程序根本没机会处理，因为你的主线程被卡死在 `accept` 这一行了！
- **如果 `listen_fd` 设置为非阻塞模式**：`accept` 发现队列空了，会立即返回 `-1`，并将 `errno` 设为 `EAGAIN`。你的程序会说：“噢，客人走了。”然后立刻回到 `epoll_wait` 继续处理那 1000 个老客户的消息。

**`listen_fd` 的非阻塞要求**：

| 模式 | 是否必须 non-blocking | 结论 |
|---|---|---|
| **select / poll** | ❌ 不是必须 | 建议设 |
| **epoll + LT** | ❌ 不是必须 | 建议设 |
| **epoll + ET** | ⭐⭐⭐ 必须 | 必须循环 accept 到 EAGAIN，阻塞 socket 会在队列空时卡死 |

## 1.2 设置 `conn_fd` 为非阻塞模式

这是最核心的要求，主要为了防止 **“部分就绪”** 和 **“慢速攻击”**。

- 风险场景 1：**数据校验失败**
    有时 `select` 告诉你数据到了，但当 CPU 尝试读取时，发现该 TCP 报文校验和（Checksum）错误，内核会丢弃这个包。此时如果 `recv` 是阻塞的，它会卡住等待下一个包。

- 风险场景 2：**写缓冲区的动态性**
    如果你要发送一个 10MB 的大文件给客户端，而客户端网络很慢。
    - **阻塞模式**：`send` 会一直卡住，直到数据全部塞进内核缓冲区。这意味着在发送期间，你无法处理任何其他客户端的消息。
    - **非阻塞模式**：`send` 能发多少发多少，发不完就返回已发送的字节数，剩下的下次再说，然后可以处理其他客户端进程的请求。

- 风险场景 3：**epoll ET 模式下的循环读取要求**
    当你需要循环读取直到读空缓冲区时，最后一次 `recv` 必定会遇到“**没数据**”的情况。非阻塞模式下它会报错返回，而阻塞模式下它会直接让你的服务器“永眠”。

**`conn_fd` 的非阻塞要求**：

| 模式 | 是否必须 non-blocking | 结论 |
|---|---|---|
| **select / poll** | ❌ 不是必须 | 建议设 |
| **epoll + LT** | ❌ 不是必须 | 建议设 |
| **epoll + ET** | ⭐⭐⭐ 必须 | 不设置的话，循环读到 EAGAIN 时会永久阻塞，卡死事件循环 |

> [!note] 初始化流程
> 1. **创建即设置**：`socket()` -> `setNonBlocking()`。
> 2. **接受即设置**：`accept()` 得到 `conn_fd` 后，在将其加入监控集合之前，立即对 `connfd` 调用 `setNonBlocking`。

# 2. 其它选项

除了非阻塞，下面几个选项在生产环境下通常这样配置：

| 选项 | 作用对象 | 核心作用 | 是否继承 | I/O 多路复用中是否必要 | 实战建议 |
|---|---|---|---|---|---|
| SO_REUSEADDR | listen_fd | 允许在 TIME_WAIT 状态下重用端口 | ❌ | ⭐ 建议 | 必须在 bind() 之前设置，高可用服务的标配。 |
| Non-blocking | 两者均可 | IO 调用立即返回，不阻塞线程 | ❌ | ⭐⭐⭐ 必须 | Reactor 模式的核心。防止 accept 或 read/write 导致整个事件循环卡死。 |
| SO_RCVBUF | 两者均可 | 设置 TCP 接收缓冲区的大小 | ✅ | ❌ 非必须 | 必须在 listen 之前设置 listen_fd 才能让 conn_fd 继承生效。大数据传输场景需调大。 |
| SO_SNDBUF | 两者均可 | 设置 TCP 发送缓冲区的大小 | ✅ | ❌ 非必须 | 影响 write 能缓存的数据量。通常由系统自动调优，手动设置需谨慎（过小会导致频繁写阻塞）。 |
| TCP_NODELAY | conn_fd | 禁用 Nagle 算法，取消发送延迟 | ❌ | ❌ 非必须 | 实时性要求高的场景（如网游、行情推算）必开。 |
| SO_KEEPALIVE | conn_fd | 开启 TCP 存活探测机制 | ❌ | ❌ 非必须 | 默认 2 小时才触发，通常需配合 TCP_KEEPIDLE 等参数缩短时间。 |
| SO_LINGER | conn_fd | 控制 close() 时未发送数据的处理逻辑 | ❌ | ❌ 非必须 | 用于规避大量 TIME_WAIT 或确保数据强制送达。 |

> 这里的“**是否继承**”指的是：在 `listen_fd` 上设置的 socket 选项，`accept()` 出来的 `conn_fd` 会不会自动拥有这些设置。

关于缓冲区设置（SO_SNDBUF/SO_RCVBUF）的补充：
1. 继承性特例：
	- 缓冲区大小在 accept 时是**可以被继承**的。
	- **关键点**：如果你希望所有新连接都拥有特定的缓冲区大小，必须对 `listen_fd` 进行设置，且必须在 `listen()` 调用之前完成。这是因为 TCP 窗口规模选项（Window Scale）是在三次握手期间确定的。
2. 系统限额：
	- 设置的值受内核参数 `net.core.rmem_max` 和 `net.core.wmem_max` 的限制。
	- 内核实际分配的空间通常是设置值的 2 倍（内核需预留一部分空间存放 sk_buff 等元数据结构）。
3. I/O 多路复用中的关联：
	- 在非阻塞 IO 中，SO_SNDBUF 的大小直接决定了 write 返回 EAGAIN 的频率。缓冲区越大，单次能“塞进”内核的数据越多。

# 3. Non-blocking 与 IO-multiplex 的协同机制

> [!question]
> 如果把 `listen_fd` 和 `conn_fd` 都设置为了**非阻塞**模式，那不是会造成服务端应用线程空转，浪费 CPU 资源吗？

会产生“非阻塞模式会导致应用线程忙等（Busy-wait）”这一误解，根源在于将非阻塞 I/O 与轮询（Polling）混为一谈。

**轮询模式（Busy-wait，错误用法）**

```cpp
// 反例：直接对非阻塞 fd 做裸轮询
while (true) {
    int cfd = accept(listen_fd, nullptr, nullptr);
    if (cfd == -1 && errno == EAGAIN)
        continue; // 无连接时立即返回，线程持续占用 CPU，CPU 利用率趋近 100%
}
```

此模式下，线程始终处于运行态，在用户态与内核态之间频繁切换，造成无效的 CPU 消耗。

**I/O 多路复用模式（epoll，正确用法）**

```cpp
while (true) {
    // epoll_wait：若就绪链表为空，将调用线程投入阻塞，让出 CPU 调度权
    int nready = epoll_wait(epfd, events, MAX_EVENTS, -1);

    for (int i = 0; i < nready; i++) {
        if (events[i].data.fd == listen_fd) {
            // 仅在 epoll_wait 返回后（即内核确认有连接就绪）才调用 accept
            // 此时 accept 为非阻塞语义：数据必然就绪，不会进入等待；
            // 即便在极端竞态条件下连接已被对端撤销（RST），也仅返回错误，不阻塞线程
            while ((cfd = accept(listen_fd, nullptr, nullptr)) > 0) { ... }
        }
    }
}
```

该模式的执行过程可划分为三个阶段：

1. **阻塞阶段（Blocked）**：当就绪链表为空时，`epoll_wait` 将调用线程置于睡眠状态，从 CPU 运行队列中摘除，不消耗任何 CPU 时钟周期。
2. **唤醒阶段（Runnable）**：网络数据包到达时，网卡触发硬件中断，内核中断处理程序（softirq）沿协议栈完成数据包处理，并通过预先注册在目标 socket 等待队列上的 `ep_poll_callback` 回调，将对应的 fd 挂入 epoll 实例的就绪链表，随后唤醒阻塞在 `epoll_wait` 上的线程，使其重新进入可运行状态。此过程仅将**就绪事件子集**拷贝至用户空间，复杂度为 $O(k)$（$k$ 为就绪 fd 数）。
3. **处理阶段（Running）**：线程被调度执行，遍历 `epoll_wait` 返回的就绪事件并调用相应的 I/O 系统调用。
	
> [!note] “阻塞”语义的分层使用
> 在 I/O 多路复用模型中，对“**阻塞**”的使用是有意分层的，两者服务于不同的目标：
> - **`epoll_wait` 的阻塞**：用于**CPU 资源保全**。在无 I/O 事件期间，使线程主动放弃 CPU，避免忙等。
> - **单个 fd 的非阻塞**：用于**隔离故障 fd 的影响**。若某个 fd 在 `epoll_wait` 返回后因竞态或对端异常导致实际不可读，非阻塞语义确保 `read` / `accept` 等调用立即返回 `EAGAIN`，而不会使整个事件循环线程陷入阻塞，从而保障其余就绪连接的服务延迟不受影响。
