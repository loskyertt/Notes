# 1. Non-blocking 设置

在严谨的 I/O 多路复用编程中，通过 `socket(...)` 获得的 `server_fd` 和通过 `accept(...)` 获得的 `conn_fd` **都建议设置为非阻塞模式**（epoll ET 模式下是**必须**），但它们应对的风险场景完全不同。

## 1.1 设置 `server_fd` 为非阻塞模式

即便 `epoll_wait` / `select` 已经告知 `server_fd` 可读（即有新连接完成三次握手），调用 `accept` 仍可能因**连接在就绪与处理之间被对端撤回**而扑空。

> [!example] 场景模拟：消失的新连接 (The Disappearing Connection)
> 假设你正在使用 `epoll` 或 `select` 监控 `server_fd`。
> 1. **事件入队**：一个客户端发起连接请求，完成 TCP 三次握手，内核将这个连接放入 `server_fd` 的全连接队列。
> 2. **就绪通知**：`epoll_wait` 返回，告知 `server_fd` 可读，意味着队列非空。
> 3. **竞态发生**：在 `epoll_wait` 返回与调用 `accept` 之间的时间窗口内，对端因进程崩溃、断电或主动发送 RST 撤销了这条连接，内核随即将其从全连接队列移除，队列重新为空。
> 4. **系统调用扑空**：此时调用 `accept` 已“扑空”——就绪事件存在，但连接已不存在。

- 如果把 `server_fd` 设置为**阻塞模式**：`accept` 发现队列为空，会陷入阻塞直至下一个新连接到来。此时主线程被卡在 `accept`，无法回到事件循环，其他就绪事件（如已连接客户端的数据读写）完全无法处理。
- 如果把 `server_fd` 设置为**非阻塞模式**：`accept` 发现队列为空，立即返回 `-1` 并将 `errno` 设为 `EAGAIN`，线程随即回到 `epoll_wait` 继续处理其他就绪事件。

**`server_fd` 的非阻塞要求**：

| 模式 | 是否必须 non-blocking | 结论 |
|---|---|---|
| **select / poll** | ❌ 不是必须 | 建议设 |
| **epoll + LT** | ❌ 不是必须 | 建议设 |
| **epoll + ET** | ⭐⭐⭐ 必须 | 必须循环 accept 到 EAGAIN，阻塞 socket 会在队列空时卡死 |

## 1.2 设置 `conn_fd` 为非阻塞模式

这是最核心的要求，主要为了应对 **就绪与读取之间的竞态**、**写缓冲区的部分就绪** 以及 **ET 模式下的循环读取要求**。

- 风险场景 1：**就绪与读取之间的竞态（TOCTOU Race）**
    `epoll_wait` 返回就绪事件到调用 `recv` 之间存在时间窗口。在这段时间内，对端可能已发送 RST 或 FIN，导致内核实际无数据可读。多线程/多进程服务器（如基于 `SO_REUSEPORT` 的多 worker 模型）中，多个 worker 可能被同一事件唤醒，但仅有一个能成功读取数据，其余 worker 在阻塞模式下将陷入死等。

- 风险场景 2：**写缓冲区的部分就绪**
    `epoll_wait` 报告 fd 可写仅表示发送缓冲区剩余空间已超过 `SO_SNDLOWAT` 阈值，并不保证能容纳完整数据。例如，发送 10MB 大文件而客户端网络很慢：
    - **阻塞模式**：`send` 在填满缓冲区后阻塞，直至剩余数据全部进入内核缓冲区，期间事件循环完全停滞，无法服务其他客户端。
    - **非阻塞模式**：`send` 返回实际写入字节数（可能远小于请求长度），未发送部分留待下次 `epoll_wait` 报告可写时继续。

- 风险场景 3：**epoll ET 模式下的循环读取要求**
    ET 模式只在状态变化时通知一次，因此读完已就绪数据的标准范式是循环调用 `recv` 直到返回 `EAGAIN`。这“最后一次”调用必然面对一个“缓冲区已空”的 fd——阻塞模式下线程会在此永久阻塞，整个事件循环随之停摆；非阻塞模式下则立即返回 `EAGAIN`，表示读空完成。

**`conn_fd` 的非阻塞要求**：

| 模式 | 是否必须 non-blocking | 结论 |
|---|---|---|
| **select / poll** | ❌ 不是必须 | 建议设 |
| **epoll + LT** | ❌ 不是必须 | 建议设 |
| **epoll + ET** | ⭐⭐⭐ 必须 | 不设置的话，循环读到 EAGAIN 时会永久阻塞，卡死事件循环 |

> [!note] 初始化流程
> 1. **创建即设置**：调用 `socket()` 成功创建 `server_fd` 后，就把 `server_fd` 设为非阻塞模式。
> 2. **接受即设置**：`accept()` 得到 `conn_fd` 后，在将其加入监控集合之前，把 `conn_fd` 设为非阻塞模式。

# 2. Non-blocking 与 IO-multiplex 的协同机制

> [!question]
> 如果把 `server_fd` 和 `conn_fd` 都设置为了**非阻塞**模式，会造成服务端应用线程空转，浪费 CPU 资源吗？

产生“非阻塞模式会引发应用线程忙等（Busy-wait）”这一误解的根源，是将**非阻塞 I/O** 与**轮询（Polling）**两种独立机制混为一谈：非阻塞只规定了 I/O 调用的返回语义（“无数据可读时立即返回 `EAGAIN`”），并不规定线程在没有 I/O 事件时该如何调度。

**轮询模式（Busy-wait，错误用法）**

```cpp
// 反例：直接对非阻塞 fd 做裸轮询
while (true) {
    int cfd = accept(server_fd, nullptr, nullptr);
    if (cfd == -1 && errno == EAGAIN)
        continue; // 无连接时立即返回，线程持续占用 CPU，CPU 利用率趋近 100%
}
```

此模式下，线程始终处于运行态，在用户态与内核态之间频繁切换，造成无效的 CPU 消耗——这是把“非阻塞”当作了“事件通知”的替代品，但二者并不等价。

**I/O 多路复用模式（epoll，正确用法）**

```cpp
while (true) {
    // epoll_wait：若就绪链表为空，将调用线程投入阻塞，让出 CPU 调度权
    int nready = epoll_wait(epfd, events, MAX_EVENTS, -1);

    for (int i = 0; i < nready; i++) {
        if (events[i].data.fd == server_fd) {
            // 仅在 epoll_wait 返回后（即内核确认有连接就绪）才调用 accept
            // 此时 accept 为非阻塞语义：数据必然就绪，不会进入等待；
            // 即便在极端竞态条件下连接已被对端撤销（RST），也仅返回错误，不阻塞线程
            while ((cfd = accept(server_fd, nullptr, nullptr)) > 0) { ... }
        }
    }
}
```

该模式的执行过程可划分为三个阶段：

1. **阻塞阶段（Blocked）**：当就绪链表为空时，`epoll_wait` 将调用线程置于睡眠状态，从 CPU 运行队列中摘除，不消耗任何 CPU 时钟周期。
2. **唤醒阶段（Runnable）**：网络数据包到达时，网卡触发硬件中断，内核中断处理程序（softirq）沿协议栈完成数据包处理，并通过预先注册在目标 socket 等待队列上的 `ep_poll_callback` 回调，将对应的 fd 挂入 epoll 实例的就绪链表，随后唤醒阻塞在 `epoll_wait` 上的线程，使其重新进入可运行状态。此过程仅将**就绪事件子集**拷贝至用户空间，复杂度为 $O(k)$（$k$ 为就绪 fd 数）。
3. **处理阶段（Running）**：线程被调度执行，遍历 `epoll_wait` 返回的就绪事件并调用相应的 I/O 系统调用。

> [!note] “阻塞”语义的分层使用
> 在 I/O 多路复用模型中，对“**阻塞**”的使用是有意分层的，两者服务于不同的目标：
> - **`epoll_wait` 的阻塞**：用于**CPU 资源保全**。在无 I/O 事件期间，使线程主动放弃 CPU，避免忙等。
> - **单个 fd 的非阻塞**：用于**隔离故障 fd 的影响**。若某个 fd 在 `epoll_wait` 返回后因竞态或对端异常导致实际不可读，非阻塞语义确保 `read` / `accept` 等调用立即返回 `EAGAIN`，而不会使整个事件循环线程陷入阻塞，从而保障其余就绪连接的服务延迟不受影响。

# 3. 其它选项

除了非阻塞，下面几个选项在生产环境下通常这样配置：

| 选项 | 作用对象 | 核心作用 | 是否继承 | I/O 多路复用中是否必要 | 实战建议 |
|---|---|---|---|---|---|
| SO_REUSEADDR | server_fd | 允许在 TIME_WAIT 状态下重用本地地址 | N/A | ⭐ 建议 | 必须在 `bind()` 之前设置，高可用服务的标配。 |
| Non-blocking (O_NONBLOCK) | server_fd 和 conn_fd | I/O 调用立即返回，不阻塞线程 | ❌ | ⭐⭐⭐ 必须 | Reactor 模式的核心。防止 `accept` 或 `read`/`write` 导致整个事件循环卡死。 |
| SO_RCVBUF | server_fd 和 conn_fd | 设置 TCP 接收缓冲区大小 | ✅ | ❌ 非必须 | 必须在 `listen()` 之前设置 `server_fd` 才能让 `conn_fd` 继承生效。大数据传输场景需调大。 |
| SO_SNDBUF | server_fd 和 conn_fd | 设置 TCP 发送缓冲区大小 | ✅ | ❌ 非必须 | 影响 `write` 能缓存的数据量。通常由系统自动调优，手动设置需谨慎（过小会导致频繁写阻塞）。 |
| TCP_NODELAY | conn_fd | 禁用 Nagle 算法，取消发送延迟 | ✅ | ❌ 非必须 | 实时性要求高的场景（如网游、行情推送）必开。 |
| SO_KEEPALIVE | conn_fd | 开启 TCP 存活探测机制 | ✅ | ❌ 非必须 | 默认 2 小时才触发，通常需配合 `TCP_KEEPIDLE` 等参数缩短时间。 |
| SO_LINGER | conn_fd | 控制 `close()` 时未发送数据的处理逻辑 | ✅ | ❌ 非必须 | 用于规避大量 TIME_WAIT 或确保数据强制送达。 |

> [!note]
> - “**是否继承**”是指：在 `server_fd` 上通过 `setsockopt` 设置的 socket 选项，`accept()` 返回的 `conn_fd` 是否自动拥有相同取值。
> - **通用规则**：Linux 内核在 `accept` 创建新 socket 时，会从监听 socket 复制绝大多数 socket 选项（包括 `SO_RCVBUF`、`SO_SNDBUF`、`SO_KEEPALIVE`、`SO_LINGER`、`TCP_NODELAY` 等）。详见 `socket(7)` 与 `tcp(7)` 手册。
> - **关键例外：`O_NONBLOCK`**：这是文件状态标志（file status flag），存储于 `struct file` 而非 `struct socket` 中，由 `fcntl` 而非 `setsockopt` 设置，因此 **不会被 `accept` 继承**。每个新 `conn_fd` 必须重新调用 `fcntl` 设置。
> - **`SO_REUSEADDR`**：虽然技术上也会被复制，但其语义仅对 `bind()` 有意义，对已建立的 `conn_fd` 无实际作用，故标记为 N/A。

对缓冲区大小（`SO_SNDBUF` / `SO_RCVBUF`）设置的补充：

1. **时序要求**
	- 若希望所有新连接继承特定缓冲区大小，必须在 `listen()` 之前对 `server_fd` 设置：因为 TCP 窗口规模选项（Window Scale）在三次握手期间协商确定。
2. **内核限额与实际分配**
	- 设置值受 `net.core.rmem_max` / `net.core.wmem_max` 限制。
	- 内核实际分配的空间通常是设置值的 2 倍（用于存放 `sk_buff` 等元数据结构）。
3. **与非阻塞 I/O 的耦合**
	- `SO_SNDBUF` 的大小直接决定了 `write` 返回 `EAGAIN` 的频率：缓冲区越大，单次能写入内核的数据越多，写阻塞的频率越低。
