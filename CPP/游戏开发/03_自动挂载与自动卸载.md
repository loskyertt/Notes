# 1. 场景树

**场景树**是一种用来管理游戏中所有对象的数据结构，是构建游戏世界架构的核心概念。虽然不同引擎（Unreal Engine、Unity、Cocos2d-x、Godot）具体实现细节不同，但核心思想一致。

- **核心结构**：树形结构，由一个个**节点（Node）**组成，有根节点，根节点下有子节点，子节点下还可以有孙节点
- **作用一：继承关系**——子节点继承父节点属性。父节点（一辆车）移动，子节点（乘客）跟随；父节点销毁，子节点随之销毁
- **作用二：逻辑分组**——方便管理，例如"敌人"节点下可以挂载"武器"、"血条"、"模型"等子节点

**图解示例：**

```text
场景树根节点
├── 主角
│   ├── 骨骼模型
│   └── 手持武器
├── 敌人
│   ├── 模型
│   └── AI控制器
└── 地形
```

# 2. 自动挂载

**含义**：当你创建一个对象并将其添加到场景树中时，引擎会**自动**调用该对象的初始化函数（如 `Start`、`Ready` 或 `BeginPlay`）。你不需要手动写 `player->init()`，只要把它"挂"到树上，它就会自动执行初始化逻辑。

> [!tip] 解决了什么问题？
> - **避免空指针**：确保对象只有在场景环境（物理系统、渲染系统）已就绪后才进行初始化
> - **解耦**：创建对象的代码不需要关心对象内部具体的初始化逻辑

---

# 3. 自动卸载

**含义**：当节点从场景树中移除时，引擎自动触发该对象的清理逻辑（如 `exitTree`、`onClean`），释放其持有的游戏资源，保持场景整洁。

根据具体场景，"自动卸载"通常涵盖以下几种行为：

- **内存与资源的自动回收**（最核心定义，由 RAII / `unique_ptr` 保证）
- **组件与脚本的生命周期管理**（`exitTree`、`onClean` 等回调按正确顺序触发）
- **游戏逻辑清理**（存档、断开网络连接、卸载 GPU 纹理等，`unique_ptr` 无法替代）

# 4. 代码实战：自动挂载

为演示场景树和自动挂载，我们用 C++ 从零构建一个极简"迷你引擎"。

**整体架构：**

```
main()
└── sceneRoot (Node: "SceneRoot")            ← unique_ptr，main 栈上持有
      └── player (Player: "主角")            ← unique_ptr，sceneRoot.m_children 持有
            └── weapon (Sword: "倚天剑")     ← unique_ptr，player.m_children 持有
```

**内存图：**

```
┌─────────────────────────────────────────────────────────┐
│  main() 的栈帧                                          │
│  sceneRoot [ unique_ptr ] ──────────────────────┐       │
└─────────────────────────────────────────────────│───────┘
                                                  │ owns
                                                  ▼
                                    ┌─────────────────────┐
                                    │   Node "SceneRoot"  │
                                    │  m_children:        │
                                    │  [ unique_ptr ] ──┐ │
                                    └───────────────────│─┘
                                                        │ owns
                                                        ▼
                              ┌──────────────────────────────┐
                              │       Player "主角"          │
                              │  m_parent: ──────────────────┼──→ Node "SceneRoot"
                              │  m_children:                 │    （裸指针，只是认识）
                              │  [ unique_ptr ] ──────────┐  │
                              └───────────────────────────│──┘
                                                          │ owns
                                                          ▼
                                        ┌─────────────────────────┐
                                        │      Sword "倚天剑"     │
                                        │  m_parent: ─────────────┼──→ Player "主角"
                                        │                         │   （裸指针，只是认识）
                                        └─────────────────────────┘
```

## 4.1 第一步：定义基类 Node

所有游戏对象（主角、敌人、摄像机）都继承自这个节点类。此处展示聚焦于自动挂载的简化版本，`getFullPath()` 等辅助方法将在第 6 节引入。

```cpp
#include <iostream>
#include <vector>
#include <string>
#include <memory>

class Node {
 protected:
  std::string m_name;
  Node *m_parent = nullptr;                       // 父节点裸指针（安全原因见下方说明）
  std::vector<std::unique_ptr<Node>> m_children;  // 独占所有子节点

 public:
  Node(std::string name) : m_name(std::move(name)) {}

  virtual ~Node() {
    // 父节点析构时，vector 析构自动销毁所有 unique_ptr，从而递归销毁所有子节点
    std::cout << ">>> 析构函数调用：[" << m_name << "] 被销毁了。\n";
  }

 public:
  // 生命周期回调：节点被挂载到树中时自动触发
  virtual void enterTree() {
    std::cout << "[" << m_name << "] 被挂载到场景树中（Node 的 enterTree() 被调用）...\n";
  }

  // 驱动整棵子树逐帧更新（框架方法）
  virtual void update(float dt) {
    onProcess(dt);                                  // ① 先执行自身逻辑
    for (const auto &child : m_children) {
      child->update(dt);                            // ② 再递归驱动所有子节点
    }
  }

  // 每帧逻辑钩子：子类重写此函数实现自身行为
  virtual void onProcess(float dt) {
    std::cout << "调用 Node 的 onProcess（一般什么都不做）\n";
  }

 public:
  // 添加子节点，接管 unique_ptr 所有权
  void addChild(std::unique_ptr<Node> child) {
    child->m_parent = this;                         // ① 建立反向链接
    m_children.push_back(std::move(child));         // ② 转移所有权进 vector
    m_children.back()->enterTree();                 // ③ 触发自动挂载回调
  }
};
```

> [!warning] **裸指针安全的关键前提**：`m_parent` 使用裸指针是安全的，条件是==父节点持有子节点的 `unique_ptr`==——父节点销毁时子节点一起销毁，子节点的 `m_parent` 裸指针永远不会成为悬空指针（Dangling Pointer）。

> [!note] **现代 C++ 惯用法：按值传参再 `move`**
>
> ```cpp
> Node(std::string name) : m_name(std::move(name)) {}
> ```
>
> 参数按**值传递（by value）**，再 `move` 进成员变量：
> - 传入左值（变量）：一次拷贝 + 一次移动
> - 传入右值（字面量）：一次移动 + 一次移动（编译器可优化为零拷贝）
>
> 比 `const std::string&` 再拷贝更高效，是现代 C++ 的惯用法。

## 4.2 第二步：创建具体的游戏对象

```cpp
// 武器：继承 Node
class Sword : public Node {
 public:
  Sword() : Node("倚天剑") {}

  void enterTree() override {
    Node::enterTree();   // ⚠️ 必须先调用父类，否则截断基础挂载逻辑（见第 10 节）
    std::cout << ">>> " << m_name
              << "：自动绑定到玩家手上，攻击力 +100！（Sword 的 enterTree() 被调用）\n";
  }

  void onProcess(float dt) override {
    std::cout << "调用 Sword 的 onProcess\n";
  }
};

// 主角：继承 Node
class Player : public Node {
 public:
  Player() : Node("主角") {}

  void enterTree() override {
    Node::enterTree();   // ⚠️ 先调用父类
    std::cout << ">>> " << m_name
              << "：我已经进入游戏世界！（Player 的 enterTree() 被调用）\n";
    // --- 自动挂载逻辑 ---
    // 无需外部传入武器，Player 自己创建并接管所有权
    auto weapon = std::make_unique<Sword>();
    this->addChild(std::move(weapon));  // 必须 std::move，unique_ptr 不可拷贝
  }

  void onProcess(float dt) override {
    std::cout << "调用 Player 的 onProcess\n";
  }
};
```

**自动挂载的精髓：**
- **时机即逻辑**：`Player::enterTree()` 里直接创建并挂载 `Sword`，`main` 函数无需介入
- **解耦**：外部只负责"把节点放进树里"；节点放入后该做什么（初始化坐标、加载资源、挂载子组件），完全由节点自己的 `enterTree()` 决定

## 4.3 第三步：运行引擎

```cpp
int main() {
  auto sceneRoot = std::make_unique<Node>("SceneRoot");

  std::cout << "--- 开始创建并挂载主角 ---" << std::endl;

  {
    auto player = std::make_unique<Player>();
    // std::move 将 player 所有权转移给 sceneRoot
    // 执行完后，main 中的 player 变量变为空指针，不再管理该对象
    sceneRoot->addChild(std::move(player));
  }

  std::cout << "\n--- 游戏主循环开始 ---" << std::endl;
  sceneRoot->update(0.1f);

  std::cout << "\n--- 程序结束，自动清理内存 ---" << std::endl;
  // main 结束 → sceneRoot unique_ptr 析构
  // → m_children vector 析构 → Player 析构 → Sword 析构
  // 整个链条自动、安全地销毁
}
```

**调用链展开：**

```
sceneRoot->addChild(player)
  └── player->enterTree()  被触发
        └── player->addChild(sword)
              └── sword->enterTree()  被触发
                    └── 打印武器绑定信息
```

# 5. 挂载阶段运行结果

```shell
--- 开始创建并挂载主角 ---
[主角] 被挂载到场景树中（Node 的 enterTree() 被调用）...
>>> 主角：我已经进入游戏世界！（Player 的 enterTree() 被调用）
[倚天剑] 被挂载到场景树中（Node 的 enterTree() 被调用）...
>>> 倚天剑：自动绑定到玩家手上，攻击力 +100！（Sword 的 enterTree() 被调用）

--- 游戏主循环开始 ---
调用 Node 的 onProcess（一般什么都不做）
调用 Player 的 onProcess
调用 Sword 的 onProcess

--- 程序结束，自动清理内存 ---
>>> 析构函数调用：[SceneRoot] 被销毁了。
>>> 析构函数调用：[主角] 被销毁了。
>>> 析构函数调用：[倚天剑] 被销毁了。
```

**析构链（内存自动清理）：**

```
main 结束
  → sceneRoot（unique_ptr）析构
      → ~Node("SceneRoot") 析构函数体先执行，打印 SceneRoot 析构信息
      → m_children（vector）成员析构
          → player（unique_ptr）析构
              → ~Node("主角") 析构函数体先执行，打印主角析构信息
              → m_children（vector）成员析构
                  → sword（unique_ptr）析构
                      → ~Node("倚天剑") 析构函数体先执行，打印倚天剑析构信息
```

> [!note] **场景树的层级管理意义**：`main` 里只销毁 `sceneRoot`，`Player` 和 `Sword` 就会随着智能指针的级联析构被全部自动销毁——这就是场景树对生命周期的管理。

# 6. m_parent 的用途

在示例代码里，`m_parent` 只被赋值，从未被读取——这是为了尽量简化示例。但在真实引擎里，`m_parent` 极其重要。

## 6.1 用途一：向上查找（获取路径）

```cpp
std::string getFullPath() const {
    if (m_parent == nullptr) {
        return "/" + m_name;                          // 根节点
    }
    return m_parent->getFullPath() + "/" + m_name;    // 递归向上
}

// 调用效果：
// sword->getFullPath() 返回："/SceneRoot/主角/倚天剑"
```

## 6.2 用途二：自杀式销毁

游戏中极其常见——子弹打中目标后销毁自身：

```cpp
void removeSelf() {
    if (m_parent != nullptr) {
        m_parent->removeChild(this);  // 通知父节点移除我
        // 执行完这行，this 指向的对象已被销毁！
    }
}
```

> [!note] 如果没有 `m_parent`，子节点**根本不知道自己挂在谁身上**，无法完成自我移除。

## 6.3 用途三：向上传递事件

```cpp
void takeDamage(int amount) {
    m_hp -= amount;
    if (m_hp <= 0 && m_parent != nullptr) {
        m_parent->onChildDied(this);  // 告诉父节点"我死了"
    }
}
```

## 6.4 用途四：判断节点是否在场景树中

```cpp
bool isInTree() const {
    return m_parent != nullptr;   // 有父节点 = 已挂载
}
```

> [!note] `m_parent` 赋予了子节点"**向上看**"的能力。没有它，每个节点就是一座孤岛，只能被动等待父节点操控，无法主动与外界交互。

# 7. update 递归调用详解

在 `Node::update()` 中加入路径打印，便于观察调用顺序（这是完整代码中的最终版本，需要 `getFullPath()` 已定义）：

```cpp
virtual void update(float dt) {
    onProcess(dt);
    for (const auto &child : m_children) {
        child->update(dt);
        std::cout << "[" << child->m_name << "] 的场景树路径：" << child->getFullPath() << "\n";
    }
}
```

当前树结构：

```
SceneRoot
└── Player "主角"
      └── Sword "倚天剑"
```

## 7.1 逐步执行模拟

调用入口：`sceneRoot->update(0.1f)`，用**缩进层级**表示调用栈深度：

```
sceneRoot->update(0.1f)
│
├─ ① sceneRoot->onProcess(0.1f)
│      → Node::onProcess：打印 "调用 Node 的 onProcess（一般什么都不做）"
│
└─ ② for (child : m_children)  → Node，唯一子节点：Player
       └─ player->update(0.1f)
             │
             ├─ ① player->onProcess(0.1f)
             │      → Player::onProcess：打印 "调用 Player 的 onProcess"
             │
             └─ ② for (child : m_children)  → Player，唯一子节点：Sword
                    └─ sword->update(0.1f)
                          │
                          ├─ ① sword->onProcess(0.1f)
                          │      → Sword::onProcess：打印 "调用 Sword 的 onProcess"
                          │
                          └─ ② for (child : m_children)  → Sword 没有子节点，不执行
                          └─ sword->update 返回 ⬆
                    └─ 打印 "[倚天剑] 的场景树路径：/SceneRoot/主角/倚天剑"
             └─ player->update 返回 ⬆
       └─ 打印 "[主角] 的场景树路径：/SceneRoot/主角"
└─ sceneRoot->update 返回 ⬆
```

对应输出：

```
调用 Node 的 onProcess（一般什么都不做）
调用 Player 的 onProcess
调用 Sword 的 onProcess
[倚天剑] 的场景树路径：/SceneRoot/主角/倚天剑
[主角] 的场景树路径：/SceneRoot/主角
```

## 7.2 注意细节：路径的打印顺序

你可能疑惑：为什么 **Sword 的路径**比 **Player 的路径**先打印？

看代码执行顺序：

```cpp
for (const auto &child : m_children) {
    child->update(dt);      // ← ① 先递归进去（子节点全部跑完）
    std::cout << ...        // ← ② 再打印路径
}
```

这是**深度优先、后序**的特性：==必须等子树全部执行完，才轮到自己后续的代码==。

- `Player` 的循环：先调用 `sword->update(dt)`（进入 Sword 世界，全部跑完），再打印 Sword 路径
- `sceneRoot` 的循环：先调用 `player->update(dt)`（进入 Player 世界，全部跑完，含 Sword），再打印 Player 路径

# 8. 代码扩展：自动卸载

自动卸载需要在 Node 及各子类中添加以下内容：

| 新增内容 | 位置 | 作用 |
| :--- | :--- | :--- |
| `exitTree()` | Node 基类（虚函数） | 节点退出场景树时的生命周期回调 |
| `onClean()` | Node 基类（虚函数，**钩子**） | 子类自定义清理逻辑的填空点 |
| `clean()` | Node 基类（**非虚**，框架方法） | 递归清理整棵子树，骨架锁死不可 override |
| `removeChild()` | Node 基类 | 主动将指定子节点从树中摘除，返回所有权 |
| `getFullPath()` / `getName()` | Node 基类 | 辅助查询方法 |
| `onClean()` override | Sword / Player | 各自释放专属游戏资源 |
| `exitTree()` override | Sword / Player | 自定义退出提示 |

## 8.1 扩展基类 Node

```cpp
class Node {
 protected:
  std::string m_name;
  Node *m_parent = nullptr;
  std::vector<std::unique_ptr<Node>> m_children;

 public:
  Node(std::string name) : m_name(std::move(name)) {}

  virtual ~Node() {
    // ✅ 析构函数只负责打印，绝不调用 clean()（原因见第 12 节）
    // unique_ptr vector 会自动析构，不需要手动 clean()
    std::cout << ">>> 析构函数调用：[" << m_name << "] 被销毁了。\n";
  }

 public:
  virtual void enterTree() {
    std::cout << "[" << m_name << "] 被挂载到场景树中（Node 的 enterTree() 被调用）...\n";
  }

  // 新增：退出场景树回调（默认实现）
  virtual void exitTree() {
    std::cout << "[" << m_name << "] 从场景树中移除（Node 的 exitTree() 被调用）...\n";
  }

  virtual void update(float dt) {
    onProcess(dt);
    for (const auto &child : m_children) {
      child->update(dt);
      std::cout << "[" << child->m_name << "] 的场景树路径：" << child->getFullPath() << "\n";
    }
  }

  virtual void onProcess(float dt) {
    std::cout << "调用 Node 的 onProcess（一般什么都不做）\n";
  }

  // 新增：清理钩子——子类 override 此函数实现自定义清理
  // 默认行为是调用 exitTree()
  virtual void onClean() {
    exitTree();
  }

 public:
  void addChild(std::unique_ptr<Node> child) {
    child->m_parent = this;
    m_children.push_back(std::move(child));
    m_children.back()->enterTree();
  }

  // 新增：移除子节点
  // 返回 unique_ptr 是为了给调用者选择权：销毁还是移动到别处（见第 13 节）
  std::unique_ptr<Node> removeChild(Node *target) {
    for (auto it = m_children.begin(); it != m_children.end(); ++it) {
      if (it->get() == target) {
        target->clean();           // 主动触发游戏逻辑清理
        target->m_parent = nullptr;
        auto node = std::move(*it);
        m_children.erase(it);      // move 后必须 erase，清除空壳（见第 13.2 节）
        return node;               // 返回所有权给调用者
      }
    }
    return nullptr;
  }

  std::string getFullPath() const {
    if (m_parent == nullptr) return "/" + m_name;
    return m_parent->getFullPath() + "/" + m_name;
  }

  std::string getName() const { return m_name; }

  // ✅ 非 virtual！框架方法（Template Method），子类无法 override，递归骨架被锁死
  // 负责：① 递归清理所有子节点 → ② 销毁子节点 unique_ptr → ③ 调用 onClean() 钩子
  void clean() {
    for (auto &child : m_children) {
      child->clean();       // ① 递归清理所有子节点（深度优先）
    }
    m_children.clear();     // ② 销毁子节点 unique_ptr（触发子节点析构函数）
    onClean();              // ③ 调用自定义清理钩子
  }
};
```

## 8.2 扩展具体游戏对象

```cpp
class Sword : public Node {
 public:
  Sword() : Node("倚天剑") {}

  void enterTree() override {
    Node::enterTree();
    std::cout << ">>> " << m_name
              << "：自动绑定到玩家手上，攻击力 +100！（Sword 的 enterTree() 被调用）\n";
  }

  void exitTree() override {
    std::cout << ">>> " << m_name << "：从场景树中移除（Sword 的 exitTree() 被调用）\n";
  }

  void onProcess(float dt) override {
    std::cout << "调用 Sword 的 onProcess\n";
  }

  // ✅ 只需 override onClean()，专注自身清理逻辑，无法破坏递归链
  void onClean() override {
    // 释放武器专属资源（卸载模型、特效等）
    std::cout << "Sword 释放专属资源\n";
    Node::onClean();   // 调用父类默认实现：触发 exitTree()
  }
};

class Player : public Node {
 public:
  Player() : Node("主角") {}

  void enterTree() override {
    Node::enterTree();
    std::cout << ">>> " << m_name
              << "：我已经进入游戏世界！（Player 的 enterTree() 被调用）\n";
    auto weapon = std::make_unique<Sword>();
    this->addChild(std::move(weapon));
  }

  void exitTree() override {
    std::cout << ">>> " << m_name << "：从场景树中移除（Player 的 exitTree() 被调用）\n";
  }

  void onProcess(float dt) override {
    std::cout << "调用 Player 的 onProcess\n";
  }

  // ✅ 只需 override onClean()，专注自身清理逻辑
  void onClean() override {
    // 释放玩家专属资源（存档、断开网络连接等）
    std::cout << "Player 释放专属资源\n";

  }
};
```

# 10. 关键点：防止 clean() 递归链被截断

`Node::clean()` 的设计意图是**递归清理整棵子树**：

```cpp
void clean() {
    for (auto &child : m_children) {
        child->clean();   // ← 期望递归向下
    }
    m_children.clear();
    onClean();
}
```

**`clean()` 设为非虚函数**，子类无法 override `clean()` 本身，递归骨架被"锁死"在框架里。子类只能 override `onClean()` 这个钩子方法，因而根本无法破坏递归链。

> [!warning] **如果 `clean()` 是虚函数，子类忘记调用父类就会导致递归链断裂**。
>
> 假设 `clean()` 是 `virtual` 的，子类只做了自己的事：
>
> ```cpp
> // ❌ 错误示例（假设 clean() 是 virtual 的）
> void clean() override {
>     exitTree();   // 只做了自己的清理，没有继续递归！
> }
> ```
>
> 这导致递归链断裂：
>
> ```
> Node::clean(Player)
>   └── child->clean() → Player::clean()（override）
>                           只调用了 exitTree()
>                           ❌ 没有继续递归到 Sword
> ```
>
> Sword 的 `exitTree()` 最终只能靠析构函数的副作用间接触发，顺序难以预测。

> [!note] **重写了父类的虚函数，就有责任决定父类的逻辑是否继续执行**。
> 不重写 → 父类逻辑自动执行；重写了 → 你全权负责，忘记调用父类就等于截断了它。
>
> 这个规律对 `enterTree()`、`exitTree()`、`onClean()` 等**所有虚函数**都成立。回头看代码里的 `enterTree()`——`Player` 和 `Sword` 都在第一行调用了 `Node::enterTree()`，原因正是如此。

# 11. 优化方案：模板方法模式（Template Method Pattern）

## 11.1 现存问题

如果 `clean()` 是虚函数，子类 override 时必须同时操心两件事：

```cpp
// ❌ virtual clean() 的 override（职责混乱）
void clean() override {
    Node::clean();   // 职责①：递归遍历  ← 必须记得调用！忘了就出 bug
    exitTree();      // 职责②：自定义清理
}
```

## 11.2 解决方案

**核心思路**：`clean()` 只负责递归遍历，设为**非虚**（子类无法 override）；`onClean()` 只负责自定义清理，设为**虚**（子类只 override 这一个）。

```
clean()    → 框架方法（Framework Method）：定义算法骨架，不可更改
onClean()  → 钩子方法（Hook Method）：子类填空，专注自身逻辑
```

```cpp
// ✅ Node 基类
void clean() {           // 非 virtual，框架方法，锁死骨架
    for (auto &child : m_children) {
        child->clean();
    }
    m_children.clear();
    onClean();           // 调用钩子
}

virtual void onClean() { // virtual，钩子方法，子类填空
    exitTree();
}

// ✅ 子类只需 override onClean()，无法破坏递归链
void onClean() override {
    std::cout << "Player 释放专属资源\n";
    Node::onClean();
}
```

## 11.3 两种方案对比

```
❌ 修改前：子类要操心两件事（virtual clean）
┌─────────────────────────────────┐
│ Player::clean()                 │
│   Node::clean()  ← 必须记得调用 │
│   exitTree()     ← 自定义清理   │
└─────────────────────────────────┘
        ↑ 忘了 Node::clean() → 递归断裂

✅ 修改后：职责明确分离（模板方法模式）
┌─────────────────────────────────┐
│ Node::clean()（非 virtual）     │
│   child->clean()  ← 框架负责    │
│   onClean()       ← 钩子入口    │
└─────────────────────────────────┘
┌─────────────────────────────────┐
│ Player::onClean()（virtual）    │
│   释放专属资源   ← 只管自己     │
│   Node::onClean()               │
└─────────────────────────────────┘
        ↑ 根本无法破坏递归链
```

> [!note] **`update / onProcess` 与 `clean / onClean` 的对称设计**
> 
> 把两对方法并排来看，结构完全一致：
> 
> ```
> update(dt)              clean()
>   ├─ onProcess(dt)        ├─ child->clean()  （递归子节点）
>   │   ← 钩子，子类填空    ├─ m_children.clear()
>   └─ child->update(dt)    └─ onClean()
>       ← 框架负责递归           ← 钩子，子类填空
> ```
> 
> **意图完全相同**：都把"如何遍历子树"和"每个节点自己要做什么"这两件事拆开——框架方法负责遍历，钩子方法留给子类填空。子类永远不需要操心递归，只需要 override 钩子。
> 
> ```cpp
> // 子类只 override onProcess()，不碰 update() 的递归逻辑
> void onProcess(float dt) override { std::cout << "调用 Player 的 onProcess\n"; }
> 
> // 子类只 override onClean()，不碰 clean() 的递归逻辑
> void onClean() override { std::cout << "Player 释放专属资源\n"; Node::onClean(); }
> ```
> 
> **唯一的差异：`update()` 是 `virtual` 的，而 `clean()` 不是。** 这是有意为之的权衡：
> 
> - `update()` 设为 `virtual`，是因为某些特殊节点可能需要完全接管自己子树的更新策略（比如暂停节点让子树停止 tick），override 整个 `update()` 是合理的扩展点
> - `clean()` 设为非 `virtual`，是因为卸载顺序的正确性要求更严格——一旦子类 override 并忘记调用 `Node::clean()`，递归链断裂会导致资源泄漏或 `exitTree()` 无法触发，后果比 `update()` 出错严重得多
> 
> 换句话说：`update()` 信任子类，允许极端情况下的 override；`clean()` 不信任子类，把递归骨架强制锁死，只开放 `onClean()` 这一个安全的填空口。

# 12. clean() 的调用时机

## 12.1 问题复现：double-clean

假设在析构函数中调用 `clean()`（一个常见的错误写法）：

```cpp
// ❌ 错误写法
virtual ~Node() {
    std::cout << ">>> 析构函数调用：[" << m_name << "] 被销毁了。\n";
    clean();   // ⚠️ 问题根源：双重清理
}
```

> [!note] 根本原因
> `clean()` 内部的 `m_children.clear()` 会触发子节点的析构函数，而析构函数又会再次调用 `clean()`，形成循环。

逐步追踪：以 Player 被析构为例

```cpp
void clean() {
    for (auto &child : m_children) {
        child->clean();       // ← 第①步：主动调用子节点的 clean()
    }
    m_children.clear();       // ← 第②步：销毁 unique_ptr，触发析构
    onClean();
}

virtual ~Node() {
    clean();                  // ← 问题根源 ❌
}
```

执行链展开：

```
Player 的 unique_ptr 被销毁
  → ~Player() 被调用，然后 ~Node() 被调用
      → clean() 第一次进入
          │
          ├─ ① for 循环：sword->clean() 被主动调用       ← Sword 第①次 clean()
          │       Sword 的 onClean() 执行，打印退出信息
          │
          ├─ ② m_children.clear()
          │       → 销毁 Sword 的 unique_ptr
          │           → ~Sword() 被调用，然后 ~Node() 被调用
          │               → clean() 再次进入             ← Sword 第②次 clean()！
          │                   → for 循环：Sword 无子节点，跳过
          │                   → m_children.clear()：空操作
          │                   → onClean()：exitTree() 再次打印！  ← 双重输出
          │
          └─ ③ onClean()：Player 的退出信息
```

这两条路都会触发 Sword 的 `clean()`：

```
路径①（主动）：Player::clean() → 遍历 → sword->clean()
路径②（被动）：m_children.clear() → ~Sword() → ~Node() → clean()
```

**本质问题：double-clean**

```
m_children.clear()
    ↓ 销毁 Player 的 unique_ptr
    ↓ 触发 ~Player()
    ↓ 触发 ~Node()，又调用 clean()
    ↓ clean() 又调用 onClean() → exitTree()
    ↓ 第二次清理！（且虚函数已退化，行为不可预期）
```

## 12.2 析构期间虚函数退化

```
析构顺序：
~Sword()   ← Sword 特有部分先销毁，vptr 退化回 Node 的版本
~Node()    ← 此时调用任何 virtual 函数，只能看到 Node 的实现
```

当 `Sword` 的析构函数运行时，**Sword 特有的部分已经被销毁**，虚函数表（vptr）退化回 `Node` 的版本。所以第二次 `clean()` 里调用的 `onClean()` 和 `exitTree()` 都是 `Node` 的版本，而不是 `Sword::exitTree()`。

## 12.3 修复方案

> [!note] **析构函数不应该调用 `clean()`！**

```cpp
// ✅ 正确写法：析构函数只负责打印，绝不主动触发游戏逻辑清理
virtual ~Node() {
    std::cout << ">>> 析构函数调用：[" << m_name << "] 被销毁了。\n";
    // unique_ptr vector 的 RAII 机制自动处理内存释放，无需手动 clean()
}
```

此时只有**一条路**：

```
~Node(Player)
  → m_children 自动析构（vector 的 RAII）
      → Sword unique_ptr 销毁
          → ~Node(Sword)
              → Sword 的 m_children 自动析构（空）
              → 结束
```

`clean()` 只在**需要主动卸载节点时**手动调用，例如在 `removeChild()` 内部：

```cpp
std::unique_ptr<Node> removeChild(Node *target) {
    for (auto it = m_children.begin(); it != m_children.end(); ++it) {
        if (it->get() == target) {
            target->clean();           // ✅ 主动触发游戏逻辑清理（正确时机）
            target->m_parent = nullptr;
            auto node = std::move(*it);
            m_children.erase(it);
            return node;
        }
    }
    return nullptr;
}
```

## 12.4 clean() 的真正价值

| | 负责人 | 时机 |
| :--- | :--- | :--- |
| **内存回收** | `unique_ptr` / OS | 自动，无需操心 |
| **游戏逻辑清理** | `exitTree()` / `onClean()` | 需要在**正确时机**主动触发 |

`unique_ptr` 的 RAII 机制保证内存安全，`main()` 结束后 OS 也会回收一切。**从内存角度，完全不需要手动调用 `clean()`**（包括在 `main()` 里也不需要手动调用 `sceneRoot->clean()`）。

`clean()` 真正的价值是触发**无法自动完成的游戏逻辑**：

```cpp
void onClean() override {
    savePlayerData();        // 存档（OS 不会帮你做）
    disconnectFromServer();  // 断开网络连接（OS 不会帮你做）
    unloadTextures();        // 卸载 GPU 纹理（OS 不会帮你做）
    Node::onClean();
}
```

**正确的 `clean()` 调用场景：**

```cpp
// ✅ 场景①：游戏运行中动态移除节点（如玩家死亡）
sceneRoot->removeChild(player);   // 内部调用 clean()，触发存档等逻辑

// ✅ 场景②：切换场景，卸载旧场景所有节点
oldScene->clean();

// ❌ 不应在析构函数里调用
// 析构已是"最后手段"，此时触发游戏逻辑为时已晚，且虚函数行为退化不可靠
```

# 13. removeChild 实现详解

```cpp
std::unique_ptr<Node> removeChild(Node *target) {
    for (auto it = m_children.begin(); it != m_children.end(); ++it) {
        if (it->get() == target) {
            target->clean();           // 主动触发游戏逻辑清理
            target->m_parent = nullptr;
            auto node = std::move(*it);
            m_children.erase(it);      // move 后必须 erase，原因见 13.2
            return node;               // 返回所有权给调用者
        }
    }
    return nullptr;
}
```

注意：对于 `if (it->get() == target)` 这里的写法：

```
it->get()     // ✅ 迭代器-> = (*it).  → unique_ptr::get() → Node*
(*it).get()   // ✅ 同上，等价写法
(*it)->get()  // ❌ unique_ptr-> 穿透进 Node，Node::get() 不存在
```

> [!tip] 💡 为什么要把所有权返回出去？

这是给调用者**选择权**：

```cpp
// 选择①：不接收返回值 → 临时 unique_ptr 在语句末销毁，节点就地析构
sceneRoot->removeChild(player);

// 选择②：接收返回值 → 调用者接管所有权，节点继续存活
auto node = sceneRoot->removeChild(player);
anotherNode->addChild(std::move(node));   // 将节点移动到另一个父节点下
```

如果 `removeChild` 内部直接销毁节点，调用者就永远失去了"把节点移动到别处"的机会。**返回 `unique_ptr` 是一种设计上的灵活性**：销毁还是复用，由调用者决定。

> [!tip] 💡 move 之后为何还要 erase？

需要区分两件事：

```
*it           → 是一个 unique_ptr 对象本身（vector 里的"格子"）
(*it).get()   → 格子里装着的裸指针（指向 Node 的箭头）
```

`std::move(*it)` 只是**掏空了格子里的内容**（裸指针变为 nullptr），**格子本身还留在 vector 里**：

```
std::move(*it) 之前：
m_children = [ unique_ptr→Player,   unique_ptr→Sword ]
                    ↑ it 指向这里

std::move(*it) 之后：
m_children = [ unique_ptr→nullptr,  unique_ptr→Sword ]
               ↑ 格子还在！只是变成了空的空壳

m_children.erase(it) 之后：
m_children = [ unique_ptr→Sword ]
               ↑ 空壳格子被移除，vector 干净
```

如果不 `erase`，vector 里会永远留着一个**空壳 `unique_ptr`**，遍历时访问空指针会产生未定义行为。

> [!note] 补充：另一种实现方式（推荐）

```cpp
void removeChild(Node *target) {
    // 假设 m_children 包含: [obj1, obj2, obj3, obj4]
    // 要删除的是 obj3
    
    // 第一步：std::remove_if
    // 遍历容器，找到要删除的元素，将其移到末尾
    // 结果: [obj1, obj2, obj4, obj3]  (obj3被移到末尾)
    // 返回新终点迭代器 (指向obj4之后)
    
    auto new_end = std::remove_if(
        m_children.begin(),
        m_children.end(),
        [target](const std::unique_ptr<Node> &p) {
            return p.get() == target;
        }
    );
    
    // 第二步：erase
    // 删除从新终点到原终点的所有元素
    // 删除 [obj3]
    // 结果: [obj1, obj2, obj4]
    
    m_children.erase(new_end, m_children.end());
    
    // erase 时 unique_ptr 析构 → 自动 delete
}
```

```cpp
#include <iostream>
#include <vector>
#include <string>
#include <memory>

// 1. 定义基础节点类
class Node {
 protected:
  std::string m_name;
  Node *m_parent = nullptr;
  std::vector<std::unique_ptr<Node>> m_children;

 public:
  Node(std::string name) : m_name(std::move(name)) {}

  virtual ~Node() {
    std::cout << ">>> 析构函数调用：[" << m_name << "] 被销毁了。\n";
  }

 public:
  virtual void enterTree() {
    std::cout << "[" << m_name << "] 被挂载到场景树中（Node 的 enterTree() 被调用）...\n";
  }

  virtual void exitTree() {
    std::cout << "[" << m_name << "] 从场景树中移除（Node 的 exitTree() 被调用）...\n";
  }

  virtual void update(float dt) {
    onProcess(dt);
    for (const auto &child : m_children) {
      child->update(dt);
      std::cout << "[" << child->m_name << "] 的场景树路径：" << child->getFullPath() << "\n";
    }
  }

  virtual void onProcess(float dt) {
    std::cout << "调用 Node 的 onProcess（一般什么都不做）\n";
  }

  virtual void onClean() {
    exitTree();
  }

 public:
  void addChild(std::unique_ptr<Node> child) {
    child->m_parent = this;
    m_children.push_back(std::move(child));
    m_children.back()->enterTree();
  }

  std::unique_ptr<Node> removeChild(Node *target) {
    for (auto it = m_children.begin(); it != m_children.end(); ++it) {
      if (it->get() == target) {
        target->clean();
        target->m_parent = nullptr;
        auto node = std::move(*it);
        m_children.erase(it);
        return node;
      }
    }
    return nullptr;
  }

  std::string getFullPath() const {
    if (m_parent == nullptr) return "/" + m_name;
    return m_parent->getFullPath() + "/" + m_name;
  }

  std::string getName() const { return m_name; }

  void clean() {
    for (auto &child : m_children) {
      child->clean();
    }
    m_children.clear();
    onClean();
  }
};

// 2. 具体游戏对象：武器
class Sword : public Node {

  }
};
```

# 15. 进阶：数据驱动的自动挂载

在更成熟的引擎（如 Unreal Engine）中，"自动挂载"还有一种更高级的含义：**基于配置文件的挂载**。

假设你有一个 JSON 文件描述主角：

```json
{
  "type": "Player",
  "components": [
    { "type": "SpriteComponent", "path": "hero.png" },
    { "type": "AudioComponent",  "sound": "step.wav" }
  ]
}
```

引擎会读取这个 JSON，利用 C++ 的**反射机制（Reflection）**或**工厂模式（Factory Pattern）**，自动 `new SpriteComponent` 和 `new AudioComponent`，并调用 `addChild` 将它们挂载到 Player 上——这也是一种"自动挂载"，常用于组件化开发，实现了数据与代码的彻底解耦。

# 16. 其他疑问

## 16.1 Q.1

> [!tip] 💡 为什么使用 unique_ptr 而非 shared_ptr？

从**高性能、严格层级**的场景树角度看，`unique_ptr` 更符合语义，也有显著性能优势。

**原因一：符合"独占所有权"语义**

场景树的核心是父子关系，通常认为：父节点拥有子节点，子节点属于且仅属于一个父节点，父节点销毁则子节点必须销毁。这完美契合 `std::unique_ptr` 的独占所有权语义。

**原因二：性能优势**

- `shared_ptr` 需要维护**控制块**（存储引用计数），内存开销更大
- `shared_ptr` 的拷贝涉及**原子操作**，在多线程环境下有额外性能开销
- `unique_ptr` 几乎零开销，等同于裸指针

| 特性 | `std::unique_ptr`（推荐用于严格层级） | `std::shared_ptr`（推荐用于灵活引用） |
| :--- | :--- | :--- |
| **所有权** | 独占（父节点拥有子节点） | 共享（多个系统可持有同一节点） |
| **性能** | 极高（无额外开销） | 较低（原子计数器开销） |
| **安全性** | 需小心裸指针悬空 | 较安全，配合 `weak_ptr` 可防循环引用 |
| **代码复杂度** | 较高（需频繁 `std::move`） | 较低（可随意拷贝传递） |

## 16.2 Q.2

Node 中的 `onClean()` 是这样写的：

```cpp
// Node::onClean() 内部
virtual void onClean() {
    exitTree();   // ← 这里没有写 Node::exitTree()，是普通的虚函数调用
}
```

Sword 中的 `onClean()` 是这样写的：

```cpp
void onClean() override {
  // 释放武器专属资源，比如卸载模型、特效等
  std::cout << "Sword 释放专属资源（Sword::onClean() 调用）\n";
  Node::onClean();
}
```

在 Sword 的 `onClean()` 中调用了 `Node::onClean()`。

> [!tip] 💡 问题：Sword 的 `onClean()` 中的 `Node::onClean()` 中,调用的是 Node 中的 `exitTree()`，还是 Sword 中重新覆写的（`override`）的 `exitTree()`？

**答案**：调用的是 Sword 的 `exitTree()`。

`Node::onClean()` 只是 **指定了从哪个类开始查找 `onClean`**，但进入函数体之后，里面的 `exitTree()` 仍然是通过 `this` 指针发起的虚函数调用。

此时 `this` 指向的对象实际类型是 `Sword`，所以：

```
Node::onClean() 被执行
    ↓
this 指针 → 实际指向 Sword 对象
    ↓
exitTree() → 查虚函数表 → 找到 Sword::exitTree()
    ↓
调用 Sword::exitTree()
```

调用链：

```
sword->onClean()          → Sword::onClean()
  └── Node::onClean()     → this 仍是 Sword 对象
        └── exitTree()    → Sword::exitTree() ✅  而不是 Node::exitTree()
```

如果你想强制调用 Node::exitTree() 必须显式加上类名限定：

```cpp
virtual void onClean() {
    Node::exitTree();   // ← 强制跳过虚函数表，直接调用 Node 的版本
}
```

但这在实际中几乎不需要这样做，通常都希望调用最派生类的版本。
