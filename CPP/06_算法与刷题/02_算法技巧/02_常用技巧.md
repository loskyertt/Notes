# 1. 位运算加速

> [!abstract] 核心结论
> 对于整数 `k`，可以用位运算替代对应的算术运算。最常见的例子是用 `k & 1` 替代 `k % 2` 判断奇偶，用 `k >> 1` 替代 `k / 2` 做整除。位运算直接操作二进制位，是 CPU 原生支持的最快基本指令之一。

## 1.1 二进制的位权原理

理解位运算的前提，是理解二进制的"位权"结构。

**十进制的类比**：以十进制数 `123` 为例：

$$123 = 1\times10^2 + 2\times10^1 + 3\times10^0$$

其中 $10^2=100$ 和 $10^1=20$ 都是 $10$ 的倍数，与最后一位无关。因此，**判断一个十进制数能否被 $10$ 整除，只需看最后一位**。

**类比到二进制**：以二进制数 `1011`（十进制 11）为例：

$$1011_2 = 1\times2^3 + 0\times2^2 + 1\times2^1 + 1\times2^0 = 8 + 0 + 2 + 1$$

> [!note] 关键发现
> $2^3=8$、$2^2=4$、$2^1=2$，它们都是 **2 的倍数（偶数）**，无论系数（对应的二进制位）是 0 还是 1，贡献的数值一定是偶数。
> **唯独 $2^0=1$ 是奇数**。
> 因此，整个数的奇偶性**完全由二进制最低位（第 0 位）决定**：
> - 最低位为 `1` → 整体为奇数
> - 最低位为 `0` → 整体为偶数

## 1.2 按位与（&）的机制

`&` 是**按位与**运算，规则为：**两个对应位均为 `1`，结果才为 `1`，否则为 `0`**。

数字 `1` 的二进制表示为 `...00000001`，只有最低位为 `1`，其余全为 `0`。

因此，`k & 1` 的作用是**屏蔽 `k` 的所有高位，只保留最低位**：

```
k = ...XXXXXXX0  （偶数，最低位为 0）     k = ...XXXXXXX1  （奇数，最低位为 1）
1 = ...00000001                           1 = ...00000001
-----------------------------             -----------------------------
结果= ...00000000  →  0（偶数）           结果= ...00000001  →  1（奇数）
```

| 判断条件 | 位运算写法 | 算术运算等价写法 |
| :--- | :--- | :--- |
| `k` 为奇数 | `(k & 1) == 1` | `k % 2 == 1` |
| `k` 为偶数 | `(k & 1) == 0` | `k % 2 == 0` |

## 1.3 常用位运算等价替换

`k & 1` 只是最简单的一例。以下是竞赛中常用的位运算等价替换汇总：

| 位运算 | 等价的算术 / 逻辑运算 | 说明 |
| :--- | :--- | :--- |
| `k & 1` | `k % 2` | 取最低位，用于奇偶判断 |
| `k >> 1` | `k / 2`（向下取整）| 右移 1 位，等价整除 2 |
| `k << 1` | `k * 2` | 左移 1 位，等价乘以 2 |
| `k >> n` | `k / (1 << n)` | 右移 $n$ 位，等价整除 $2^n$ |
| `k << n` | `k * (1 << n)` | 左移 $n$ 位，等价乘以 $2^n$ |
| `k & (k - 1)` | 清除 `k` 的最低有效位（最低的那个 `1`）| 可用于判断 `k` 是否为 2 的幂次 |
| `k & (-k)` | 提取 `k` 的最低有效位（lowbit）| 树状数组（BIT / Fenwick Tree）的核心操作 |

> [!warning] 负数与移位的注意事项
> - 上述移位等价关系对**负数**不完全成立。C++ 标准在 C++20 之前规定，负数右移的行为是**实现定义（implementation-defined）**；C++20 起才明确为算术右移（高位补符号位）。竞赛中若操作数可能为负，务必先确认语义，或改用算术运算。
> - `k & (k - 1) == 0` 且 `k > 0`，可判断 `k` 是否为 2 的整数次幂（`k == 0` 时该式同样成立，需单独排除）。

## 1.4 性能对比

| 运算 | CPU 指令类型 | 相对开销 |
| :--- | :--- | :--- |
| `k % 2`（取模）| 除法（`DIV` / `IDIV`）| 高（除法是最慢的基本算术指令之一）|
| `k / 2`（整除）| 除法（`DIV` / `IDIV`）| 高 |
| `k >> 1`（右移）| 移位（`SHR` / `SAR`）| 极低（通常单周期完成）|
| `k & 1`（按位与）| 逻辑与（`AND`）| 极低（通常单周期完成）|

> [!info] 关于编译器优化
> 现代编译器（GCC / Clang）开启 `-O2` 后，通常会将 `k % 2`、`k / 2` 自动优化为等价的位运算，大多数评测环境下两者性能差异可忽略不计。
> 即便如此，手写位运算仍有价值：一是体现对底层原理的理解；二是在极少数未开启优化的环境下保留显式性能优势；三是某些操作（如 `lowbit`）语义本身就是位运算，写成位运算反而更清晰。

# 2. Fast I/O

## 2.1 默认 I/O 慢的根源

C++ 的 `cin/cout` 默认速度慢，原因有两个独立的机制：

- **与 C 标准 I/O 同步**：为保证 `cin/cout` 与 `scanf/printf` 混用时输出不会乱序，C++ 默认将两套 I/O 体系绑定在同一缓冲区上，并在每次操作时维护同步状态，引入了大量额外开销。

- **`cin` 与 `cout` 互相绑定（tie）**：默认情况下，每次调用 `cin >>` 之前，都会先自动 `flush`（刷新）`cout`，确保提示信息在用户输入前显示到屏幕上。这在交互式命令行程序中是合理的，但在竞赛的批处理（文件重定向）场景下是纯粹的性能浪费。

## 2.2 三条加速语句

将以下三行写在 `main()` 函数的**最开头**，且在任何 I/O 操作之前：

```cpp
#include <iostream>
#include <vector>

int main() {
    std::ios::sync_with_stdio(false);  // ① 关闭与 C stdio 的同步
    std::cin.tie(nullptr);             // ② 解除 cin 与 cout 的绑定

    // ... 你的代码 ...

    std::cout << answer << '\n';       // ③ 用 '\n' 代替 std::endl
}
```

**逐条解析：**

- **① `std::ios::sync_with_stdio(false)`**
  关闭 `cin/cout` 与 `scanf/printf` 的同步，使 C++ 流拥有独立的缓冲区。速度可从比 `scanf` 慢数倍，提升至基本持平。**此调用必须发生在任何 I/O 操作之前，否则行为未定义。**

- **② `std::cin.tie(nullptr)`**
  将 `cin` 的绑定输出流设为空（`nullptr`），取消每次 `cin >>` 前的自动 `flush`，消除不必要的缓冲区刷新开销。

- **③ `'\n'` 代替 `std::endl`**
  `std::endl` = 输出 `'\n'` + **立即强制刷新缓冲区**（调用 `flush()`），每次调用都触发一次系统调用，开销极大。改用 `'\n'` 后，换行字符进入缓冲区，由系统在合适时机统一刷新，效率大幅提升。

## 2.3 使用限制与注意事项

> [!caution] 禁止混用 cin/cout 与 scanf/printf
> 开启 `sync_with_stdio(false)` 后，**严禁在同一程序中同时使用 `cin/cout` 和 `scanf/printf/puts/getchar` 等 C 函数**。
> 两套 I/O 体系各自维护独立缓冲区，混用会导致读写顺序错乱，产生极难复现和调试的错误。选定一套并贯穿全程使用。

> [!caution] 交互题（Interactive Problem）禁用 Fast I/O
> 交互题中，评测机需要实时收到你的输出后，才能给出下一步输入。此时必须在每次输出后**立即刷新缓冲区**：
> ```cpp
> std::cout << your_answer << std::endl;   // 或
> std::cout << your_answer << '\n' << std::flush;
> ```
> 由于 `cin.tie(nullptr)` 会禁用自动 flush，**交互题不应使用 Fast I/O 全套方案**，或至少需要手动在每次输出后显式刷新。

# 3. 多组数据的输入流同步

## 3.1 输入流的物理模型

竞赛题目中，**所有测试数据在程序启动前就已全部写入输入流**（文件或标准输入的管道），不存在"边运行边手动输入"的情况。

输入流可以抽象为一个**有序数据队列**，由一个"读取指针"从左到右依次消费。`cin >>` 每被调用一次，指针就向后推进一格读走一个数据。

**核心认知**：`return` 或 `continue` 只是转移了程序的控制流，**不会让队列中的数据消失，也不会移动读取指针**。未被读走的数据，将原封不动地留在队列中，等待下一次 `cin >>` 来消费。

以如下输入文件为例：

```
2       ← 共 2 组数据
1       ← 第 1 组：n = 1
7       ← 第 1 组：a[0] = 7（客观存在于输入流，无论程序是否读它）
2       ← 第 2 组：n = 2
3 4     ← 第 2 组：a[0] = 3, a[1] = 4
```

队列视图：

```
[ 2 ][ 1 ][ 7 ][ 2 ][ 3 ][ 4 ]
  ↑
 读取指针起始位置
```

## 3.2 错误示例：提前退出导致指针偏移

```cpp
// ❌ 错误：在读完当前组数据前提前 return
void solve() {
    int n;
    std::cin >> n;

    if (n == 1) {
        std::cout << "YES\n";
        return;  // 致命！直接跳出，后续数据未被读取
    }

    for (int i = 0; i < n; ++i) {
        int val;
        std::cin >> val;  // n == 1 时，此循环根本不会执行
    }
}
```

**逐步追踪（以上述输入文件为例）：**

```
第 1 组 solve() 调用：
  cin >> n  →  读到 1，指针移动到 [7]
  n == 1    →  输出 YES，直接 return
  [7] 未被读取，指针停留在 [7]

第 2 组 solve() 调用：
  cin >> n  →  本应读下一组的 n=2
              实际读到的是 [7]（上一组的残留元素！）
              程序误以为 n = 7，尝试读取 7 个元素
              → 数据不足，卡死在读入，最终 TLE 或 RE
```

> [!caution] 连锁反应
> 一旦某组数据的读取指针发生偏移，**之后所有组的数据都将错位**。错误会随组数累积放大，且表现为 TLE / RE 而非 WA，极难通过调试单独定位到根因。

## 3.3 正确示例：先读完，再处理

```cpp
// ✅ 正确：无论逻辑如何，先将本组全部数据读入，再做判断
void solve() {
    int n;
    std::cin >> n;

    std::vector<int> a(n);
    for (int i = 0; i < n; ++i) {
        std::cin >> a[i];  // 保证所有元素都被读走，指针正确推进
    }

    // 数据已全部读完，此后的 return 不再影响输入流
    if (n == 1) {
        std::cout << "YES\n";
        return;  // 安全：指针已正确推进到下一组起始位置
    }

    // 正常处理逻辑...
}
```

**逐步追踪：**

```
第 1 组 solve() 调用：
  cin >> n      →  读到 1
  for 循环      →  读取 1 个元素，[7] 被正确消费，指针推进
  n == 1        →  输出 YES，return
  指针正确停在第 2 组 n=2 的位置 ✓

第 2 组 solve() 调用：
  cin >> n      →  正确读到 2
  for 循环      →  正确读取 [3] [4] ✓
```

## 3.4 金律

> [!tip] 处理多组数据的金律
> **无论函数内部触发了何种提前退出（特判、剪枝、边界情况），都必须在退出前，将属于当前这组数据的所有输入完整读取完毕。**
>
> **实践建议**：将 `solve()` 函数明确分为两个阶段——
> 1. **读取阶段**：无条件将本组全部数据读入变量，此阶段不插入任何 `return`。
> 2. **处理阶段**：基于已读入的数据进行所有逻辑判断，此时的 `return` 是安全的。

# 4. `using` 替代 `#define`

> [!abstract] 在 C++ 编程中，`using ll = long long;` 比 `#define ll long long` 更好。

这是两者的区别：

|**特性**|**#define**|**using (或 typedef)**|
|---|---|---|
|**本质**|预处理文本替换|编译器类型别名|
|**作用域**|全局（直到文件末尾）|遵循 C++ 作用域（局部/命名空间）|
|**模板支持**|不支持|**支持**|
|**类型检查**|无类型检查|有类型检查，更安全|
|**推荐程度**|逐渐过时|**现代 C++ 推荐标准**|

下面是详细原因说明。

## 4.1 遵循作用域规则（Scope）

- **`#define`**：是**预处理器指令**。它在编译之前的预处理阶段进行简单的文本替换。它**没有作用域限制**，一旦定义，除非遇到 `#undef`，否则在整个文件甚至包含它的文件中都有效。这可能会导致命名污染。
    
- **`using`**：是**类型别名声明**。它遵循 C++ 的**作用域规则**。如果你在某个函数内部定义 `using ll = long long;`，它只在该函数内有效。

`#define` 只是简单的文本替换，有时会因为缺少括号导致逻辑错误，或者在处理指针、多个声明时出现歧义：

```cpp
#define PINT int*
PINT a, b; 
// 预处理后变成：int* a, b;
// 结果：a 是指针，b 是普通的 int！

using PInt = int*;
PInt a, b;
// 结果：a 和 b 都是指针。
```

## 4.2 更好的可读性与报错信息

- **`#define`**：编译器看到的只是替换后的结果。如果代码报错，错误信息可能会指向替换后的内容，有时会让人困惑。
    
- **`using`**：别名会被编译器记录在符号表中。在调试器（Debugger）或复杂的错误报告中，编译器往往能更好地识别并显示这个别名的含义。

## 4.3 支持模板（关键区别）

这是 `using` 最强大的地方。`using` 可以用于模板别名，而 `#define` 或 `typedef` 做不到。

```cpp
// 使用 using 可以很方便地定义模板别名
template <typename T>
using Vec = std::vector<T>;

Vec<int> myVec; // 等价于 std::vector<int>
```

如果你用 `#define` 尝试模拟模板，逻辑会变得非常混乱且难以维护。
